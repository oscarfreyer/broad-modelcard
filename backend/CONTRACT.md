## Vocabulary: UI words and contract terms

Added in v1.5. The UI uses one word per concept; the contract keeps its terms, so no field or parameter was renamed.

| **Function** | `use_case` | What the system is used for, e.g. "Discharge letter generation". Its `function_category` groups functions. |

A specific setting shows only the results stored for it. |

About population groups; never about study quality (§22). |
| **Effects on outcomes** | data set kind `effects`, `Effect`, `listEffects`, `ConceptMetrics.effects` (v1.13, §27) | What using an AI system changed for patients or care against a comparator, from a randomized trial, a prospective study, or a real-world deployment, with its design-specific risk of bias (RoB 2, ROBINS-I). ## 1. Change process

- v1 is frozen. A change to `openapi.json` or to this document is one coordinated change: update both files, the backend, `frontend/src/api/dataClient.js`, the frontend contract test, and the backend drift test.
- Additive, optional response fields may be added without a version bump. Removing or renaming fields, changing meaning, or adding required request parameters needs `/api/v2`.

## 2. Dataset versions and staged reads

- The dataset version is a positive integer that increases with every publish or rollback across all data set kinds.
- Every read endpoint accepts `version=live` (default) or `version=staged:<upload_id>`. A staged read layers one valid staged upload over the live data, for that request only. It never changes live data. The first staged read sets the upload's `previewed` flag.
- Read responses carry `X-Dataset-Version` (`<n>` or `staged:<upload_id>`) and a strong `ETag`. Live responses may be cached by the client until the version changes.
- A staged read of an upload that is not `valid` returns 409 `upload_not_valid`.
- A staged read is the live version at the time of the request, with the upload's content set in place of the live set of the same data set (and model and use case). It is not a snapshot: a publish of another data set shows through.
- A staged read of an unknown upload id returns 404 `unknown_upload`; one of an upload that is `checking`, `invalid`, `published`, `discarded`, or `superseded` returns 409 `upload_not_valid`. A version that is neither `live` nor `staged:<upload_id>` returns 422 `invalid_version`.
- Staged responses carry `X-Dataset-Version: staged:<upload_id>` and `dataset_version` `staged:<upload_id>`. Their ETags and server caches are keyed by the upload, its staged content set (a check run again writes a new one), and the live version, so live and staged responses never mix and a re-checked upload never serves its earlier set.
- A staged **merge** upload (v1.7, §11.2) was applied to the live set of its data set at check time. Once a publish or rollback replaces that set, staged reads, `getUploadChanges`, and `publishUpload` of it return 409 `upload_outdated` until the backend has checked it again on the new live set (it does so at once; `getUpload` shows `checking`, then `valid` or `invalid`).
- The `ETag` covers the body; responses carry `Cache-Control: no-cache`. A matching `If-None-Match` (weak comparison, lists and `*` allowed) returns 304 with the same `ETag` and `X-Dataset-Version`. Problem responses carry neither header.
- **Ontologies (v1.13, §23).** The atlas reads take an optional `ontology=<id>`. Such a response carries `X-Ontology: <id>` and `ontology: {id, name}` in its body, and its ETag and response cache are keyed by the ontology as well; ICD-11 reads (no parameter, or `ontology=icd11`) carry neither and are byte for byte what they were before. It combines with `version` and `population`.
- **Local results (v1.13, §26).** A read for a local population also serves that population's local results of the card (a second layer beside its tiers). Its ETag and caches are keyed as for the population (the local results set belongs to the version), so a read without `population`, or for a population without local results for the card, is byte for byte what it was before.
- **Local populations (v1.10, §21).** The prevalence-dependent reads take an optional `population=<id>`. Such a response carries `X-Population: <id>` and `population: {id, name}` in its body, and its ETag and every server cache (response cache, version context, catalogue tiles) are keyed by the population and its content set as well as the version, so default and local answers never mix. A default read carries neither and is exactly what it was before populations existed. `version=staged:<upload_id>` combines with `population`: the population is looked up in the staged version (§21).

## 3. Filters

- `use_case` is the source `task_mode`. `context` is the care setting (v1.14, §29): a value of the Context axis, `Clinical` (Any setting, the first axis value and the default) or a specific setting. Every read that takes a lens takes it; a response's `filters.context` (and a row's `context`) names the setting it was read for. Before v1.14 it was always `Clinical`.
- Lens parameters default to `All ages`, `All sexes`, `All ethnicities`, and `Clinical` (v1.14). Values outside the axes return 422 `invalid_lens` (the client used to silently fall back to the first axis value).
- An unknown `model`, or a `use_case` the model lacks, returns 404 `unknown_model` / `unknown_use_case`.
- Parameter validation (422) precedes lookups (404). The problem `type` is `urn:broad-modelcard:problem:<code>`.
- `selected` is comma-separated, with at most 12 non-empty ids (otherwise 422 `invalid_selection`). Unknown ids return 404 `unknown_concept`; chapters and blocks in it are ignored.

## 4. Metric rows

### 4.1 Source decoding (normalization)

Source tuples follow the 13-field `row_format`: `perf, ci_low, ci_high, evidence_grade, n_samples, n_sites, n_studies, peer_reviewed_studies, validation_type, in_intended_use, intended_use_coverage, intended_use_level, warnings`. The row index of a combination is `age_idx×18 + sex_idx×6 + eth_idx`, with axes in the order listed in `/meta`; since v1.14 (§29) a combination of a specific care setting adds `setting_idx×90` (Any setting is index 0, so every earlier index is unchanged).

- `perf`, `ci_low`, `ci_high`: kept when finite, otherwise null. No clamping.
- `n_samples = max(24, round(x))`; `n_sites = max(1, round(x))`.
- `in_intended_use` is true for `1`, `'1'`, or `true`. Coverage falls back to 1 or 0 from that flag.
- `intended_use_level` aliases: `not_covered` → out of scope; `partial`/`low`/`middle`/`large` → partially in scope; `full` → in scope. Otherwise it is derived from coverage (≤ 0 out of scope, ≥ 0.9999 in scope, partially in scope in between), and otherwise from the flag.
- **No intended-use value (v1.11).** `in_intended_use`, `intended_use_coverage`, and `intended_use_level` are all null when the card has no intended-use statement (`intended_use_defined` false, §11.1), or when the stored row gives none (blank In intended use and Intended-use level cells in an upload; stored with the empty level `''`, §11). Such a row also drops the warning `out_of_scope_group`, which states intended use.
- **Validation data present** means `validation_type` is truthy and the warnings do not include `no_validation_data`. If it is absent, `evidence_grade`, `validation_type`, `n_studies`, and `peer_reviewed_studies` are null; `n_samples` and `n_sites` are kept.
- If validation data is present:
  - **validation_type:** the stored type normalized through the reference aliases; otherwise the type implied by the stored grade (A multisite … F internal); otherwise `internal_test`.
  - **n_studies:** the stored value when positive; otherwise estimated as `round(n_samples / 260)` for clinical types (`/ 360` otherwise), clamped to 1–18.
  - **peer_reviewed_studies:** the stored value clamped to 0–`n_studies`; otherwise `min(n_studies, round(n_studies × r))` with r = 0.88 multisite, 0.80 single-site, 0.68 benchmark, 0.56 vignette, 0.44 simulation, 0.32 internal.
  - **Grade:** derived (§4.2), and `evidence_signal` is the penalized signal. When `n_samples` or `n_studies` is missing, the stored grade is served and `evidence_signal` is null.
- Warnings pass through in stored order.

### 4.2 Derived evidence grade

The API serves the derived grade. The stored source grade differs for about 30% of validated rows; serving it would change what users see.

`signal = 0.33·type + 0.17·studies + 0.12·sites + 0.18·peer + 0.20·size − penalties`

- **type:** multisite 1.00, single-site 0.85, benchmark 0.72, vignette 0.60, simulation 0.50, internal 0.40.
- **studies:** ≥ 12 → 1.00, ≥ 8 → 0.90, ≥ 5 → 0.78, ≥ 3 → 0.64, otherwise 0.50.
- **sites:** 0.65 for non-clinical types. Otherwise ≥ 20 → 1.00, ≥ 10 → 0.86, ≥ 5 → 0.72, ≥ 2 → 0.58, otherwise 0.45.
- **peer:** `0.4 + 0.6·(peer_reviewed / studies)`, plus 0.08 if studies ≥ 8 or 0.04 if studies ≥ 4.
- **size (n_samples):** ≥ 3000 → 1.00, ≥ 1800 → 0.90, ≥ 900 → 0.78, ≥ 400 → 0.64, ≥ 150 → 0.50, ≥ 50 → 0.38, otherwise 0.26.
- **penalties:** −0.05 if prevalence score < 0.15. −0.04 if `chapter_no = '06'` and use case is exactly `Clinician Facing CDSS` *(quirk)*.
- **Local populations (v1.10, §21):** a read for a local population uses that population's prevalence score in the −0.05 penalty for the codes it lists. The formula, threshold, and bands are unchanged; local prevalence feeds the existing formulas.
- **Study adjustment (v1.13, §22):** a stored row linked to a study record adds, with the penalties and before the final clamp to 0–1, **+0.05** when the study's reporting guideline was followed (`yes`) and **−0.10** for a high, **−0.04** for a some-concerns or unclear, and 0 for a low risk of bias. A row without a linked study adds nothing and grades exactly as before. The term weights (`/meta.evidence_signal_weights`) and these adjustments (`/meta.evidence_study_adjustments`) are published.
- **grade:** A ≥ 0.90, B ≥ 0.80, C ≥ 0.68, D ≥ 0.56, E ≥ 0.44, otherwise F.

### 4.3 Performance grade

Computed from `perf` clamped to 0–1: A ≥ 0.9, B ≥ 0.8, C ≥ 0.7, D ≥ 0.6, E ≥ 0.5, otherwise F. Null when `perf` is null.

### 4.4 Overall score, grade, and tier

- **Tier, first match wins:** no row → `no_data`. Out of scope or `in_intended_use` false → `out_of_scope`. No evidence grade → `no_evidence_data`. No `perf` → `no_performance_data`. Otherwise `graded`. A row without an intended-use value (§4.1, v1.11) is never out of scope, so a card without an intended-use statement never has the tier `out_of_scope`.
- **Score** (graded only): `0.35·gs(performance_grade) + 0.20·perf + 0.30·gs(evidence_grade) + 0.15·iu`, where `gs`: A 1.00, B 0.85, C 0.70, D 0.55, E 0.40, F 0.25, and `iu`: in scope 1, partially in scope 0.6, out of scope 0. The four weights are published in `/meta.overall_score_weights` (`performance_grade`, `perf`, `evidence_grade`, `intended_use`), so the frontend can explain the score without restating them.
- **Score without intended use** (v1.11): for a row without an intended-use value, on a card without an intended-use statement or a row that gives none on a card with one, the intended-use term is dropped and the other three are scaled to 100%: `(0.35·gs(performance_grade) + 0.20·perf + 0.30·gs(evidence_grade)) / 0.85`. These weights are published in `/meta.overall_score_weights_without_intended_use` (`performance_grade`, `perf`, `evidence_grade`). Rows with an intended-use value keep the formula above exactly. Bands and grade cut-offs are unchanged.
- **Grade:** A ≥ 0.88, B ≥ 0.76, C ≥ 0.64, D ≥ 0.52, E ≥ 0.40, otherwise F.
- `perf` is clamped to 0–1 in both terms, and the score to 0–1. The grade uses the unrounded score; the served score is rounded to 3 decimals. §8's weakest-row ranking uses this score for any row with `perf` and an evidence grade, whatever its tier.

### 4.5 Status vocabulary (new in v1, presentation of existing grades)

Grade letters map to statuses: **A, B → `strong`; C → `moderate`; D, E, F → `weak`**. The resulting score bands are prototype heuristics, published in `/meta.status_bands`:

| View | strong | moderate | weak |
|---|---|---|---|
| Overall (score) | ≥ 0.76 | 0.64 – 0.76 | < 0.64 |
| Performance (`perf`) | ≥ 0.80 | 0.70 – 0.80 | < 0.70 |
| Evidence (signal) | ≥ 0.80 | 0.68 – 0.80 | < 0.68 |

Per view, preserving the pre-refactor coloring semantics:

- **overall:** tier `no_data` → `no_data`; `out_of_scope` → `out_of_scope`; `no_evidence_data` → `no_data` (`not_validated` before v1.11); `no_performance_data` → `no_data`; `graded` → status of the overall grade.
- **performance:** no row or null `perf` → `no_data`; otherwise status of the performance grade. Scope is ignored, as before *(quirk)*.
- **evidence:** no row or null evidence grade → `no_data` (`not_validated` before v1.11); otherwise status of the evidence grade.
- **One missing state (v1.11).** The API no longer serves `not_validated`: the status vocabulary is `strong`, `moderate`, `weak`, `out_of_scope`, `no_data` (`/meta.statuses`), in rows, maps, summaries, catalogue distributions, lookup, multimorbidity, and exports. The tier `no_evidence_data`, the warning `no_validation_data`, and the safeguard `evidence-missing` are unchanged; only the status changed.
- **intended_use:** reported as `intended_use_level`, not as a status. A missing row, and since v1.11 a row without an intended-use value (§4.1), is reported as null. The frontend renders a condition without a row as **No data** on every view, including Intended use (V1, 2026-10-12; before, it was drawn like out of scope).

### 4.6 Warnings and safeguards

The backend returns codes with relevance or priority; the frontend owns all titles and patient/expert text.

- **Warning relevance:**
  - High: `out_of_scope_group`, `clinician_review_required`, `performance_below_target`, `no_performance_data`, `no_validation_data`.
  - Medium: `wide_confidence_interval`, `limited_validation_depth`, `rare_condition_low_support`, `mental_disorders_high_variance`, `multimorbidity_synthetic_demo`, `limited_multimorbidity_evidence`, `multimorbidity_validation_gap`.
  - Low: `conservative_rollup_p20`.
  - Unknown codes are Medium. The API orders warnings by relevance, then code. The reference ordered by relevance, then display title; titles are frontend copy, so the frontend re-sorts by title for display (clarified 2026-10-08).
- **Warning share** (v1.4): on an aggregated row (a rollup, §6, or a lens fallback over several rows, §7), each warning carries `share: {count, total}`: how many of the `total` aggregated rows carry the code. For `out_of_scope_group`, a row also counts when it is not fully in scope. Warnings about the aggregate itself (`conservative_rollup_p20`) have no share, nor do stored rows, anchor rows of stored rows, and rollups without children. A share does not change which warnings are kept.
- **Safeguards** (rules on the served row, in this order; changed in v1.4, §12.1):
  - Critical: `scope-stop` (out of scope); `perf-missing` (no `perf`).
  - Important: `scope-partial` (partially in scope); `perf-low` (`perf` < 0.7); `ci-wide` (`ci_high − ci_low` > 0.14); `evidence-weak` (evidence grade D, E, or F); `evidence-missing` (`perf` present, no evidence grade, not out of scope; new in v1.4); `cdss-governance` (use case `Clinician Facing CDSS` or `CDSS`).
  - When none of those applies: `overall-weak` (Important, new in v1.4) if the overall status (§4.5) is `weak`; `standard-monitoring` (Routine) if it is `strong` or `moderate`. `standard-monitoring` never appears on any other status.

## 5. Concepts, anchors, prevalence

- **Levels:** 0 chapter (21), 1 block (225), 2 category (13,442). Of the categories, 2,400 have `depth_in_kind = 1`: the top-level conditions and primary metric anchors. Deeper categories (depth 2–3) have the block as `parent_id` and their depth-1 stem as `metric_anchor_id`.
- **Deeper categories** serve their anchor's row with `concept_id` replaced; `provenance.source = anchor`. If the anchor is not a depth-1 level-2 concept, `metrics` is null.
- **Local populations (v1.10, §21):** for a read with `population`, a level-2 concept the population lists takes the population's tier (and so its score); every other concept keeps the default tier. Block and chapter means follow.
- **Prevalence tiers map to scores:** very_rare 0.04, rare 0.12, uncommon 0.25, common 0.45, very_common 0.70, clamped to 0.03–0.97. For level-2 concepts the tier score replaces the stored `prevalence_score`. Block prevalence is the unweighted mean of the block's level-2 concepts, deeper categories included. Chapter prevalence is the unweighted mean of its block means (corrected 2026-10-08 after Track A1 found the reference computes it recursively, `App.jsx` `conceptPrevalenceById`).
- **Other ontologies (v1.13, §23).** These levels, anchors, and tiers describe ICD-11, the default and the storage key of every result. ICD-10-CM and MONDO, when a store imported them, have the same three-level shape and are read with `ontology=<id>`; their conditions take the tier of the ICD-11 concept they map to (§23).

## 6. Rollups (blocks and chapters)

- **Children:** the top-level depth-1 conditions under the block or chapter that have a row for the lens. A chapter aggregates conditions directly, not its blocks. `rollup.child_count` counts them; `lens_fallback` is true if any child fell back.
- **Weights:** child prevalence score. A missing, non-finite, or non-positive weight counts as 1. A read for a local population weights with its scores (v1.10, §21; approved by D14).
- **perf:** for use cases `Clinician Facing CDSS` and `CDSS`, the unweighted 20th percentile with linear interpolation (`provenance.rollup.aggregation = p20`). Otherwise the weighted mean. Rounded to 3 decimals.
- **CI:** half-width `h` is the weighted mean of child half-widths (+0.006 for CDSS). Only when `perf` is present and some child has both bounds: `ci_low = clamp(perf − h, 0, perf)`, `ci_high = clamp(perf + h, perf, 1)`, rounded to 3 decimals.
- **Counts:**
  - `n_samples` and `n_sites`: weighted mean over children having both, then `n_samples = max(24, round(·))` and `n_sites = max(1, round(·))`.
  - `n_studies`: `max(1, round(mean))` of the children's studies (inferred from samples when null); otherwise estimated from the rollup's `n_samples`.
  - `peer_reviewed_studies`: unweighted mean, clamped or estimated as in §4.1.
- **validation_type:** the type whose score (§4.2) is nearest the mean type score (first in §4.2 order on ties); null if no child has a recognized type.
- **Intended use:** coverage = `(in + 0.5·partial) / n`, rounded to 4 decimals; level is derived from coverage (§4.1). Since v1.11, `n` counts the children that have an intended-use value; when none has one, the rollup's intended-use fields are null. On a card without an intended-use statement they are always null, also for a rollup without children (which then is not out of scope).
- **Evidence grade:** derived (§4.2) only when `perf`, `n_samples`, `n_sites`, and `validation_type` are all present, using the weighted mean prevalence (missing values as 0) and the rollup's `chapter_no`. Otherwise `evidence_grade`, `evidence_signal`, `validation_type`, `n_studies`, and `peer_reviewed_studies` are null.
- **Study adjustment (v1.13, §22):** the derived signal adds the prevalence-weighted mean (the weights above) of the children's study adjustments, a child without a linked study counting 0. When no child links a study the mean is exactly 0 and nothing changes. A concept read serves it as `appraisal.study_adjustment` with `study` null.
- **Warnings:**
  - A code is kept when at least `max(1, ceil(0.3·n))` children carry it.
  - `out_of_scope_group` is added only when the rollup is fully out of scope.
  - `conservative_rollup_p20` is always added for CDSS.
  - The list is sorted. Each warning except `conservative_rollup_p20` carries a `share` over the children (§4.6, v1.4).
- **No children:** all metric fields are null, the row is out of scope, and the warnings are `out_of_scope_group`, plus `conservative_rollup_p20` for CDSS; `rollup.child_count` is 0. This happens whenever no condition under the block or chapter has a row for the lens, for example every rollup of a card that stores only the all-population lens (a product) read at a specific group such as `Age 65+`. A rollup without children is served as before for parity; clients present it as **No data**, not Out of scope (§13, V1). Since v1.10 the `MetricMap` carries the count as its trailing `child_count` column (§10), so the map can tell such a rollup from one whose conditions are genuinely out of scope (`child_count` > 0) without a concept read.

## 7. Demographic fallback

Used only when the set does not define the requested lens combination; complete 90-combination files never trigger it. A defined combination without a row for the concept has no data. **Within a setting (v1.14, §29):** the expansion keeps the requested care setting, so a group at a specific setting is combined only from narrower groups stored at that setting, never from Any setting or another setting; a setting the set defines no combination for has no data.

- Each `All …` axis in the request expands to its specific values; only combinations the set defines are expanded.
- **One row found:** served as stored, relabelled with the requested lens.
- **Several rows found:**
  - `perf`, `ci_low`, and `ci_high` are means of their non-null values, rounded to 3 decimals; the CI is not clamped around `perf`.
  - Counts follow §6 without weights.
  - Coverage is `(in + 0.5·(n − in − out)) / n`, rounded to 4 decimals.
  - Evidence is re-derived when `perf` and a validation type are present; since v1.13 the signal adds the unweighted mean of the rows' study adjustments (§22; rows without a linked study count 0).
- **Level:** in scope if all rows are, out of scope if all are, otherwise partially in scope. Since v1.11 only rows with an intended-use value count (in the coverage too); when none has one, the intended-use fields are null and `out_of_scope_group` is removed.
- **Warnings:** unioned and sorted. `out_of_scope_group` is added unless all rows are in scope, and removed otherwise. Each carries a `share` over the rows found (§4.6, v1.4).
- **None found:** no data.
- `provenance.lens_fallback = true` (new, additive).

## 8. Multimorbidity

- **Canonical selection:** each concept maps to its depth-1 anchor. The set is deduplicated, sorted (locale compare), and joined with `+` to form `combination_key`. Selection order is preserved in `selected` for display.
- **Stored combinations:** sets with fewer than 2 ids are ignored; the first duplicate wins. Label is the stored label, or the preferred terms joined with ` + `.
- **Combination row:** the exact lens row if stored, otherwise the §7 expansion. If the set defines none of the expanded combinations, the all-population row is served with `provenance.lens_fallback = true` (previously unflagged). Since v1.14 (§29) that all-population row is the one of the requested setting: a combination has a row at a specific setting only where the set stores one for that setting (normally none), and at a setting the set stores nothing for, `candidate_ids` and the `display` rows are empty.
- **Combination size:** `/multimorbidity/combination` needs at least two distinct conditions after canonicalization (otherwise 422 `invalid_selection`).
- **Candidates:**
  - No selection: every concept in any combination.
  - With a selection: the extra concept of each stored combination with size `selection + 1` that contains the whole selection.
  - Sorted by preferred term.
- **Display rows (`display` map):**
  - A selected concept shows the full selection's row (needs ≥ 2 selected; otherwise empty).
  - At depth ≥ 1, a candidate shows the row for `selection + candidate`.
  - At depth 0, a candidate shows the *weakest* row among all combinations containing it.
  - Blocks and chapters show the weakest over their conditions.
  - "Weakest" ranks: performance by `perf`; evidence by grade (A = 6 … F = 1); intended use by in scope 3, partially 2, otherwise 1 (no intended-use value, v1.11: like null); overall by score. Null counts as +∞ (never weakest). Ties keep the first. The weakest row is chosen **separately for each view**: in a `display` map row, each view's columns come from the row that is weakest for that view, so one map row can combine different combinations (clarified 2026-10-08; both tracks implement it this way).
- `display.rows` lists only concepts in scope that have at least one non-null view.
- `has_multimorbidity = false` when the model/use case declares no multimorbidity data; candidates are then empty.

## 9. Search

Case-insensitive substring match of the trimmed query against `icd11_code` (or `concept_id` when there is no code), or against `pt + ' ' + fsn + ' ' + concept_id`, over all concepts. `limit` defaults to 80; `total` counts all matches.

Since v1.12 the matches are ranked best first (§12.1); before, they were ordered by level, then preferred term, so "diabetes" led with "Hypoglycaemia in the context of diabetes mellitus". Ranks, with the query and the code (`icd11_code`, else `concept_id`) compared case-insensitively and the preferred term without a leading "- ":

1. the code is the query;
2. the code starts with the query;
3. the preferred term is the query;
4. the preferred term starts with the query, or holds it as a whole word or words (a word is a run of letters and digits);
5. a word of the preferred term starts with the query;
6. any other match (inside a word, the fully specified name, or the concept id).

Within ranks 1–2, shorter codes come first, then the code. Within ranks 3–6, shorter preferred terms come first, then the lower level, then the preferred term. Ties keep concept order. Which concepts match and `total` are unchanged; only the order and so which matches fall within `limit` changed.

- A query that is empty after trimming returns 422 `invalid_query`. The response's `query` is the trimmed query.
- A null `fsn` contributes an empty string. The reference would have matched the text "null"; no current ICD-11 concept has a null `fsn`.
- **Synonyms (v1.14, §31).** In ICD-11 (no `ontology`, or `icd11`), when the store imported synonyms (§23, §31), a concept that none of ranks 1–6 matches but one of whose synonyms holds the query is a further match, **after every match above**: ranked by how its best synonym matches (the synonym is the query; it starts with the query or holds it as whole words; a word of it starts with the query; any other match), then shorter synonyms, the lower level, the preferred term, and concept order. Such a result is the concept record plus `match: "synonym"` and `matched_term` (the synonym); every other result is the record as before. `total` counts these matches too, and `limit` cuts them after the others. A store without synonyms (no ontology import) answers every search byte for byte as v1.13 (`tests/test_search_synonyms.py` pins digests); with synonyms, a query no synonym holds answers as before as well.
- **Per ontology (v1.13, §23).** With `ontology=<id>` the search runs over that ontology's concepts with the same rules and ranks; the code is the ontology's own (the ICD-10-CM code or section, the MONDO id, an ICD-10-CM chapter's number), and the results are that ontology's concept records. Without the parameter, or with `ontology=icd11`, the search is the ICD-11 search above, unchanged.

## 10. Response budgets

- No response other than `/export/*` and admin file downloads exceeds 2 MB.
- Budgets are uncompressed body sizes. Since v1.12 responses of 1 KB and more travel gzipped when the request accepts gzip (`Content-Encoding: gzip`, `Vary: Accept-Encoding`); archives, spreadsheets, PDFs, media, and event streams are sent as they are. The ETag and `X-Dataset-Version` are those of the uncompressed body, and a 304 has no body (`tests/test_compression.py`).
- `/metrics/map` is columnar and returns all four views and, since v1.7, the trailing `safety` column, so switching the metric view (or to the Safety view) needs no request. Since v1.10 a further trailing column, `child_count`, gives a block or chapter row's `rollup.child_count` (null for condition rows and for multimorbidity `display` rows, which are not rollups, §8); 0 marks a rollup without children (§6). Clients read columns by name from `columns`, never by position. The atlas map of the demo store is about 250 KB.
- The client never downloads a full metrics table.
- `/catalogue` stays under **300 KB** and answers a warm request within **150 ms** (`tests/test_api_budgets.py`, seed and demo store). It is built once per dataset version (§17).
- `lookup` with 12 codes stays under **50 KB** and answers a warm request within **50 ms** (§19; `tests/test_lookup.py`, demo store).
- `getCardRecord` (v1.14, §32.1) stays under **300 KB**, as JSON and as JSON-LD, for every card of the demo store (`tests/test_card_record.py`; measured about 10–20 KB). `callCdsService` (§33) answers at most 12 conditions per request, from the same per-concept derivations as `lookup`.
- `getConceptSubgroups` (v1.13, §24) stays under **20 KB** (about 8 KB: twelve lens entries) and answers an uncached request within **150 ms** p95, chapters included (`tests/test_api_budgets.py`).
- `interpretQuery` (v1.14, §31) answers a warm request within **150 ms** (p95 over the 30-query quality set; an uncached query too) and stays under 20 KB (`tests/test_interpret.py::test_interpretation_budget`, demo store with the pinned ontology files). Measured: about 1–2 ms per query once the word index is built (about 30 ms, once per backend), answers of 1–6 KB. `searchConcepts` with synonyms keeps the search budget (< 150 ms warm; measured about 4 ms).
- `getSubgroupSummary` (v1.14, §24) stays under **50 KB** (about 10 KB: eleven groups with up to five flagged conditions each) and answers a warm request within **150 ms** (`tests/test_subgroup_summary.py::test_budget`, demo store; measured about 1 ms). Its first read of a card and population derives the card's rows at twelve lenses over every depth-1 condition: about 0.25–0.55 s on the demo store, once per version.

Measured on the pinned releases: the MONDO overview is about 1.2 MB and its largest chapter read ("cancer or benign tumor", 4,745 conditions) about 1.7 MB, so MONDO's conditions carry no `fsn` (their name and id are in `pt` and `code`); ICD-10-CM's overview is about 0.6 MB (`tests/test_ontologies.py::test_real_sources_reach_the_r0_coverage` checks every chapter when the releases are downloaded).
- `getComparison` (v1.13, §25) with four cards stays under 2 MB and answers a warm request within **300 ms** at atlas and chapter scope (`tests/test_comparison.py::test_comparison_budgets`, demo store). Measured: atlas about 40 KB, the largest ICD-11 chapter about 0.45 MB, MONDO's largest chapter (826 rows) about 1.3 MB.
- Reads at a specific care setting (v1.14, §29) keep the same budgets (`tests/test_demo_settings.py`, demo store): the atlas map is about 250 KB at any setting, and a setting switch is one map read and one summary read, each keyed by the setting in its ETag and cache.
- Reads for a local population (v1.10, §21) keep the same budgets: no response over 2 MB, the catalogue under 300 KB, and map, summary, and concept reads within the interaction budgets (`tests/test_api_budgets.py::test_population_reads_within_budgets`, demo store, measured with and without the population). Since v1.13 (§26) a population with local results for the card serves them within the same budgets; the map adds one aligned `layer` array.

## 11. Admin semantics

All admin operations are local-only like the rest of the API (§16). backend/README.md documents the templates and every validation rule for maintainers.

- **Data sets:** `models` (the registry; its entry and configuration fields are in §11.1), `prevalence`, `safety` (the safety incidents, v1.7, §18), and, per model and use case (the upload's *target*), `metrics` and `multimorbidity`; since v1.10 also `population`, one per local population id (its target, §21); since v1.13 also `studies` (the study records, §22), `effects` (the intervention effects, §27), `local_metrics` (per card and local population, §26), and `model_cards` (the narrow model cards, one global set, §26). A **replace** upload (the default) replaces the whole data set (or the target's data): rows missing from the file are removed, and the change summary says so. A **merge** upload (v1.7, `mode=merge`, for `metrics`, `prevalence`, `safety`, and since v1.13 `studies`, `effects`, and `local_metrics`) changes only its rows (§11.2).
- **One staged upload per data set** (per model and use case for `metrics` and `multimorbidity`). A staged upload is `checking`, `invalid`, or `valid`. A second upload returns 409 `staged_upload_exists` unless `replace_staged=true`, which marks the old one `superseded`. `discardUpload` marks a staged upload `discarded` (409 `upload_not_staged` otherwise). Neither ever touches live data.
- **Uploads:** CSV or XLSX only (415 `unsupported_file_type`, judged by extension and content), at most 128 MB (413 `upload_too_large`). A metrics or multimorbidity upload without `model_version` and `use_case` returns 422 `invalid_parameter`. The check runs in the background; `getUpload` reports `progress` (0–1) until the status is `valid` or `invalid`.
- **Evaluation results (v1.14, §32.2).** An upload may also be of kind `evaluation_results` (`Upload.kind` is the schema `UploadKind`: the data set kinds plus this one): one JSON file of a benchmark or harness run for one card, sent as text to `createEvaluationUpload` (`POST /admin/uploads/evaluation-results`, at most 1 MB), checked in the background, and **never a data set**: it has no content set, no staged read, change summary, or publish (409 `upload_not_valid`, saying that it publishes nothing), and it is not listed by `listDatasets`. A valid one offers proposed records (`getEvaluationProposals`). One staged per card (and per card in a submission); `replace_staged` supersedes it. Staged evaluation results are checked again after a registry publish or rollback. Store migration `0015_evaluation_results.sql` adds the kind to the uploads table.
- **Validation** applies the same rules as the contract; blocking errors make the upload `invalid`. A **prevalence replace** upload that would remove the tiers of more than half of the codes the live default prevalence lists is blocked with `prevalence_incomplete` (a whole-file problem, row 0); its fix names the counts and points to Local populations (§21) for a local list and to a merge upload ("Add or change rows", §11.2) for a few changes. Merge uploads and `population` uploads are not affected. **Performance needs evidence (v1.11):** a metrics or multimorbidity row (replace, merge, or records upload) with a Performance value and no validation data (§4.1: Validation type empty, or the warning `no_validation_data`) is the blocking error `performance_without_evidence`; its problem names the condition and says what is missing. The seed import (version 1) is not an upload and is exempt; its rows without evidence read No data (§4.5). **Intended use is optional per row (v1.11):** In intended use and Intended-use level may both be empty (with Intended-use coverage empty too); the row then has no intended-use value (§4.1). One of the two without the other stays `missing_value`. Error groups carry a plain-language `fix`; at most 20 examples per group. Example rows are spreadsheet row numbers (the first line of the file is 1); 0 means the whole file (an empty file, the wrong template, or an unknown target). Notes never block.
- **Targets:** the target must be in the live registry, or in a staged registry upload (then a note says it appears once that upload is published). A registry upload is invalid while one of its use cases has no performance metrics (`use_case_without_metrics`), so a new model's metrics are published before its registry entry. Staged registry uploads are checked again after a metrics publish or a rollback, staged safety and (v1.13) studies and effects uploads after a registry publish or a rollback (their cards and model versions must exist), staged effects uploads also after a studies publish or rollback (their studies and designs must hold, §27), and staged merge uploads whenever their base set stops being live (§11.2).
- **Annotated files** are available once the check has finished and while the file is kept (not after `discarded` or `superseded`, nor for a file the check found patient-level, which is deleted at once (§21): 409 `upload_not_staged`; while `checking`: 409 `upload_not_valid`). Either format can be requested for either upload format. They add a Problems column, which uploads ignore.
- **Templates:** `filled=true` returns the live data in template form (with `model_version` and `use_case` for metrics and multimorbidity: 422 `invalid_parameter` without them, 404 for an unknown model or use case). Filled metrics and prevalence templates carry each row's source in Source, Study, and Source date (§11.3). Uploading a filled template unchanged gives a valid upload with no changes, except (since v1.11) a filled metrics or multimorbidity template that still holds seed rows with performance and no evidence: those rows are rejected (`performance_without_evidence`), so such a card is corrected with a merge upload of the rows it changes, or its evidence is added first.
- **Wording (v1.7):** the registry data set is titled "AI systems & functions"; its template headers "Use case" and "Default use case" are now "Function" and "Default function" (the old headers stay accepted). Problem texts, instructions, and version summaries use the UI words (AI system, function, card). Codes and JSON keys are unchanged.
- **Care settings (v1.14, §29).** The metrics and local results templates have an optional **Setting** column after Ethnicity (aliases `Context`, `Care setting`): empty, `Any setting`, or `Clinical` store a row for Any setting; `Emergency department`, `Intensive care`, `Inpatient ward`, `Outpatient clinic`, `Primary care` (or their codes, e.g. `emergency_department`) store it for that setting only. Other values are the blocking error `unknown_setting`, whose fix names the settings. Files without the column keep every row at Any setting. A replace upload needs common lens coverage over its **Any-setting** rows only (`incomplete_lens_coverage`); rows of a specific setting may cover any conditions and groups, as evidence exists. A merge that adds a setting the stored data lacks notes `new_lens_group` with the setting in its label. Filled templates write each row's setting (`Any setting` for the rest), so they upload back unchanged. The multimorbidity template has no Setting column.
- **Change summary** (`getUploadChanges`, only for `valid` uploads, otherwise 409 `upload_not_valid`): rows are compared by key with the live data of the same data set: (condition, lens) for metrics, (condition set, lens) for multimorbidity, the ICD-11 code for prevalence and for a population (against the live set of the same population, none for a new one; v1.10), (model, use case) for the registry, the incident id for safety, the study id for studies, the effect id for effects (v1.13). Since v1.7 a metrics or prevalence row also counts as changed when only its source changes (§11.3), and a merge upload's `unchanged` counts only the rows it touched (its other rows are copies of the live ones). `models` and `use_cases` are filled for registry uploads only; use cases are written `<model_version> / <use_case>`. `base_version` is the live version compared against.
- **Row samples** (v1.4): `rows.samples` names up to 50 added, changed, and removed rows each. Metrics: (condition, lens), in lens then condition order, with the condition's name and ICD-11 code; since v1.14 (§29) a row of a specific care setting adds its `setting`, and `rows.settings` counts added, changed, and removed rows per specific setting the upload touches (metrics and local results; absent when it touches Any setting only). Prevalence: the ICD-11 code with the condition's name, in file order. Multimorbidity: (combination, lens), named by the combination label. Registry: `<model_version> / <use_case>`. Safety (v1.7): the incident id, named `<incident_id>: <summary>`, with its first condition (or chapter), first code, and lens. Studies (v1.13): the study id, named `<study_id>: <title>`, without condition, code, or lens. Effects (v1.13, §27): the effect id, named `<effect_id>: <outcome>`, with its first condition (or chapter) and first code, without lens. The counts stay authoritative; a sample list is shorter when a count exceeds 50.
- **Status shifts** compare depth-1 conditions at the all-population lens for overall, performance, and evidence statuses and for intended-use level (`no_data` when a condition has no row). Metrics: the target's rows. Multimorbidity: the display rows with nothing selected (§8). Prevalence: every model and use case of the registry; a condition counts once per (view, from, to). Population (v1.10): like prevalence, but comparing the default answers with the answers for the staged population, which is what a reader sees when switching to it; computed even when the rows equal the live population's. Studies (v1.13): like prevalence, every card whose rows link a study before or after the publish (other cards cannot shift), computed when a study is added, changed, or removed. Registry, safety, and (v1.13) effects: none (safety incidents and effects never change grades). `sample_concept_ids` lists up to 50 conditions. `targets` (v1.4) splits each shift by model and use case, most conditions first, each with its own `count` and up to 50 `sample_concept_ids`; metrics and multimorbidity shifts have exactly one target, their own. A prevalence shift's `count` is at least its largest target's count and at most their sum.
- **Publish** is atomic and serialized: one transaction adds the version, and a publish or rollback while another runs returns 409 `publish_in_progress`. A publish never leaves a partially updated version. Only a `valid` upload can be published (409 `upload_not_valid`). If live data changed so that the upload no longer fits (its target left the registry, a registry upload's use case lost its metrics, or a merge upload's base set is no longer live), it returns 409 `upload_outdated`. The version records `previewed` when the request says so or a staged read previewed the upload, and the optional change note (§11.5).
- **Initial import:** the legacy JSON import is dataset version 1 and covers every kind, so its `VersionEntry.kind` is null.
- **Rollback** of version *n* publishes a new version whose content for that kind equals version *n*: the registry, prevalence, safety, or (v1.13) studies or effects set (a version before the first safety, studies, or effects publish has no incidents, studies, or effects), every metrics (or multimorbidity) set of every model and use case, or (v1.10) every local population (a version before the first population publish has none). It takes the optional change note in its JSON body (§11.5). The optional `kind` parameter chooses the data set; without it, the kind version *n* changed, or every kind for a version that covers all (version 1). The optional `every_kind=true` (v1.11) restores every data set in one new version; combined with `kind` it returns 422 `invalid_rollback`. The new version's `kind` is the restored kind (null when every kind is restored) and its `rollback_of` is *n*. A rollback that would leave registry use cases without metrics returns 409 `rollback_conflict`. A rollback whose chosen data sets are already those of version *n* (the restored state equals the live state, set for set) returns 409 `rollback_no_change` and adds no version (v1.11). History is never deleted; unknown versions return 404 `unknown_version`.
- **History:** `listVersions` is newest first; with `kind` it lists the versions that changed that kind plus those that cover every kind. Each entry carries its change `note` (null when none was given).
- **Data sets:** `listDatasets` gives, per kind (five since v1.7, six since v1.10, eight since v1.13), the latest version that changed it (or covers all) and its time, counts (`models`, `use_cases`; `codes`; `use_cases`, `metric_rows`; `use_cases`, `combinations`, `metric_rows`; `incidents`, `open`; `populations`, `codes`; `studies`; `effects`), the newest staged upload, and all staged uploads newest first (`staged_upload_ids`).
- **Uploads** must contain aggregate synthetic metrics only. Patient-level or real patient data must never be uploaded; templates and the UI say so.

### 11.1 Registry entries and configurations (v1.5)

The registry (`models` data set) holds one record per entry and use case. Since v1.5 it carries these optional fields; the seed has none of them, and registry files without the columns stay valid.

- **Entry fields** (one value per entry, repeated on each of its rows): `kind` (`model` or `product`; empty is `model`, and `listModels` always sends it), `ai_type` (`llm`, `imaging`, `tabular_risk`, `rule_based`, `hybrid`), `developer` (text, ≤ 200 characters; fictional names only in this demonstration), `release_date` (ISO date `YYYY-MM-DD`), `description` (≤ 280 characters), `built_on` (model versions, separated by `;` in files; a list in the API, empty for models).
- **Intended-use statement** (v1.11, one value per model × use case): `intended_use_defined`, template column **Intended use stated** (Yes/No; an empty cell or a file without the column means Yes, so every earlier registry file stays valid). "No" says the card has no intended-use statement (a broad model): every intended-use field of the card is null and its rows score without intended use (§4.1, §4.4). Stored as 0 for No and NULL otherwise (migration `0006_intended_use_statement.sql`); `listModels` and the catalogue always send it. It is part of the configuration's registry signature (§11.1 change summary, §17).
- **Configuration fields** (one value per model × use case): `function_category` (`decision_support`, `documentation`, `image_analysis`, `triage`; since v1.14 also `patient_communication` and `administrative`, labels "Patient communication" and "Administrative", §28) and the developer declarations `declared_intended_purpose` (≤ 500 characters), `declared_regulatory_status` (≤ 200), `declared_contact` (≤ 200), `declared_documentation_url` (`http://` or `https://`, ≤ 500). `listModels` sends `declarations` as an object with all four fields, or null when none is given. Declarations are the developer's statements, shown as such; demonstration data never claims "certified" or "approved".
- **Validation** (blocking errors with a plain-language fix): `unknown_kind`, `unknown_ai_type`, `unknown_function_category` (values outside the lists; readable labels and codes are both accepted), `invalid_date` (not a calendar date `YYYY-MM-DD`; XLSX date cells are accepted), `invalid_url` (not http or https), `invalid_value` (too long or with a line break), `built_on_for_model` (an entry that is not a product lists `built_on`), `unknown_built_on` (a `built_on` value that is the product itself, not in the same file, or a product). Entry fields must be equal on every row of an entry (`inconsistent_value`; an empty cell counts as a different value), as for display name and status.
- **Card names (2026-10-21).** A model version or a function (use case) must not contain `|` or `,`: card ids join the two with `|` (`card_id`, §17) and `getComparison` lists card ids with `,` (§25), so a card with such a name could not be compared. Every registry upload (a file, the records upload, and the registry part of a developer submission, §26.3) refuses it with the blocking error `separator_in_name` on the Model version or Function cell, fix "Use a name without | or ,"; `createSubmission` refuses such a `model_version` with 422 `invalid_parameter`. The display name and every other field may contain both. The seed and the demo pack use neither (`tests/test_card_names.py`). A registry published before this rule keeps its names; its next registry upload must rename them.
- **Configurations and lineage (v1.14, §28).** The entry field `replaces` (template column Replaces) and the configuration fields of the configuration record (Configuration ID to Fine-tuning), `performance_measure`, `reference_standard`, and the data-protection declarations `declared_data_use`, `declared_data_location`, `declared_retention`, `declared_privacy_contact`. All optional; files without the columns stay valid. Fields, limits, and the issues `invalid_configuration_id`, `invalid_sha256`, `too_many_tools`, `replaces_self`, `unknown_replaces`, and `replaces_cycle` are in §28.
- **Change summary:** a configuration (registry row) counts as changed when any of its model's fields or its own fields change (since v1.14 also `replaces` and the §28 fields); an entry counts as changed in `models.changed` when any of its fields or configurations change. Filled templates carry the fields, so uploading one unchanged gives no changes.
- **Storage:** nullable columns on the registry tables (migration `0003_registry_entries.sql`); content sets stay immutable. A store from before v1.5 is migrated in place the first time the API starts.
- The `cdss-governance` safeguard, the p20 rollup, and the chapter-06 quirk stay keyed on the use-case strings (§4.2, §4.6, §6), not on `kind` or `function_category`.

### 11.2 Merge uploads (v1.7)

`createUpload` takes `mode` (`replace`, the default, or `merge`) for `metrics`, `prevalence`, and `safety`; another kind with `mode=merge` returns 422 `invalid_parameter`. The one-staged-upload rule (§11) is unchanged: a merge is the data set's staged upload.

- **Rows.** A merge row adds its record or replaces the stored one; a row with **Action** `Remove` deletes its key (metrics: code and lens; prevalence: code; safety: incident id); records the file does not name stay exactly as they are. Removal therefore needs the explicit marker. A Remove row in a replace upload is the error `remove_in_replace`; removing a key that is not stored is the note `nothing_to_remove`. An empty Action (or "Add or replace") adds or replaces.
- **Sources.** Every metrics or prevalence merge row that adds or replaces a record needs **Source**, **Study**, and **Source date** (ISO date); a missing one is the error `missing_provenance`. A safety incident's own fields serve as its source (Source reference, Study ID, and its Updated date, else Reported date); Study ID is required when Source type is Study (`missing_study_id`), in every mode.
- **The newest study replaces** (D9). A merge row whose source date is older than the stored row's is kept out and listed as the note `newer_study_kept` ("the newer study stays"); a stored row without a date (the seed) is always replaced. For safety the dates compared are the incidents' updated (else reported) dates.
- **Lens groups.** A metrics merge may add rows for a lens combination the set does not define yet; the set then defines it (note `new_lens_group`), and conditions without a row for it read No data there (§7).
- **Content.** A merge is applied at check time to the live set of its data set (and target): the staged set is a new immutable content set that copies the live one with the merge applied (the copy runs in SQL). The staged set records that base. When a publish or rollback replaces the base, the upload is checked again on the new live set (§2, §11).
- **Change summary.** Counts and samples cover the touched keys only: `added`, `changed`, `removed`, and `unchanged` (merge rows that changed nothing). The version summary is written like any other.

### 11.3 Row sources (v1.7)

Every stored metrics and prevalence row has a source: `{source, study, date}`.

- Rows of the seed import read **"Seed (synthetic, version 1)"** (no study, no date). Rows of a replace upload carry the Source, Study, and Source date of their row (all optional; a Study or Source date needs a Source), else `Upload <file name>` with the upload's date. Merge rows carry theirs (§11.2); copied rows keep theirs.
- Storage: interned sources (`provenance_sources`), a default source per content set (`set_provenance`), and per-row side tables (`metric_row_provenance`, `prevalence_provenance`) for the rows whose source differs from the set's default (migration `0004_safety_merge_provenance.sql`).
- Served: `getConceptMetrics` and `exportConcept` add `provenance.data_source` to the row: the stored row's source for a condition (or a deeper category through its anchor) at the requested lens; null for aggregated rows (rollups, lens fallback). Other operations leave it out. Filled templates carry every row's source (§11).
- A source-only change counts as a changed row in the change summary (§11).

### 11.4 Records upload (v1.7)

`createRecordsUpload` (`POST /admin/uploads/records`) takes JSON `{kind, model_version?, use_case?, mode: "merge", records: [...], replace_staged?}` for `metrics` (with its card), `prevalence`, `safety`, or (v1.13) `studies` and `effects`. It is the one-record form's and the helper's way into the update workflow.

- Each record is an object keyed by template column key or header (`incident_id` or `"Incident ID"`) with text, number, boolean (`Yes`/`No`), or null values; 1 to 5,000 records, a body of at most 8 MB (413 `upload_too_large`). An unknown or repeated field, another kind, or another mode returns 422 `invalid_parameter`; 409 `staged_upload_exists` as for files.
- The backend writes the records as a template-form CSV (header in row 1, record *i* in row *i* + 2, file name `<kind>-records.csv`) and checks it exactly like an uploaded file. Report examples keep the row and add `record`, the record's index. The Upload has `origin: "records"` (files: `"file"`) and `mode: "merge"`.

### 11.5 Change notes (v1.7)

`publishUpload` (`PublishRequest.note`) and `rollbackVersion` (an optional JSON body `{note}`) take a change note of at most 500 characters as sent (422 beyond); whitespace is then collapsed, and an empty note is none. The note is stored on the version and served as `VersionEntry.note`; the version `summary` keeps describing the change. The Data Library asks for a note on every publish; the API keeps it optional.

## 12. Quirks preserved for parity (review before any real use)

- The evidence-grade penalty for chapter 06 applies only to the exact use case `Clinician Facing CDSS`, not `CDSS`.
- A "rare island" penalty exists in code but can never trigger.
- The performance view ignores intended-use scope.
- The dataset export's `summary` uses a different overall formula (`0.5·perf + 0.35·evidence + 0.15·iu`, with partial = 0.5) from §4.4.
- Multimorbidity files currently store only the all-population lens, so every specific lens falls back (now flagged).

### 12.1 Intentional deviations from the reference implementation

Approved by the user on 2026-10-10. The parity tests apply exactly these deviations to the reference output (`tests/parity.py`, `reference_safeguards`) and fail on any other difference.

- **Safeguards (§4.6):** `evidence-missing` is added for rows with `perf` but no evidence grade that are not out of scope. `standard-monitoring` ("current profile is stable") requires a Strong or Moderate overall status; a Weak row with no other safeguard gets `overall-weak` instead. In the reference, a rollup with Strong performance but no evidence could read "stable" while it was Not validated.
- **Warning share (§4.6, §6, §7):** additive. The warning codes and their order are unchanged.
- **Search order (§9, v1.12):** the same concepts match and `total` is unchanged; matches are ranked best first instead of by level and preferred term. The parity test compares the match set and the total (`tests/test_api_parity.py`); `tests/test_search_ranking.py` pins the order.
- **Synonym matches (§9, §31, v1.14):** on a store with imported synonyms, ICD-11 search also matches concepts by a synonym, after every other match, so the match set and `total` grow by those concepts. The parity tests run on the seed import, which has no synonyms, so they still compare the v1.13 match set; `tests/test_search_synonyms.py` pins the order and fields of synonym matches.
- **One missing state (§4.5, v1.11):** a row without an evidence grade reads `no_data` where the reference read `not_validated`. The parity tests map the reference's `no_evidence_data` tier to `no_data`. The D3 score (§4.4) and null intended use do not apply to the seed, whose cards all state their intended use.

## 14. Scopes, summary, and exports

Added 2026-10-08 from Track A2; describes the implemented and tested behavior.

- **Scopes:**
  - `scope=atlas` covers all blocks, then all top-level conditions.
  - `scope=chapter` covers the chapter's blocks, then its level-2 concepts, in concept order.
  - `chapter_id` is required for `scope=chapter` (422 `missing_chapter_id`), must name a chapter (404 `unknown_concept`), and is ignored for `atlas`.
- **Summary:**
  - For `view=intended_use`, `counts` holds only `no_data` and `out_of_scope`, and `intended_use_counts` counts conditions with a row by level. Since v1.11 a condition without an intended-use value counts as `no_data`, and `intended_use_counts` is null for a card without an intended-use statement.
  - For `view=safety` (v1.7), `counts` is all zero and `safety_counts` counts the conditions by safety mark at the lens (`serious`, `caution`, `none`), overall and per chapter (§18).
  - `chapters` lists the chapters that have conditions, in chapter order.
  - `appraisal_counts` (2026-10-21, §22) and, since v1.14, `configuration_counts` (§28.5) are sent together, only when at least one graded condition rests on a study record, on every view; the sum of `configuration_counts` is `appraisal_counts.linked`.
  - `weighted_distribution` (v1.14, §30) is sent only for `weights=prevalence`: each status's share of the prevalence weight of the depth-1 conditions. A summary read without `weights` is byte for byte what it was.
- **Concept export:** `code` is `icd11_code`, else `concept_id`. `block` is `block_id`, else a block's own id. `hierarchy` is the preferred terms from chapter to concept. Since v1.14 (§29) `exportConcept` takes `context`; `context.setting` names a specific setting (absent for Any setting) and `model_card.context` is the setting.
- **Dataset export:**
  - `metrics_by_key` maps `concept_id|use_case|context|age | sex | ethnicity|model_version` to the served `MetricRow`, for every defined lens with a row. Key order carries no meaning. Since v1.14 (§29) `context` is the row's setting (`Clinical` for Any setting), so a card with rows at a specific setting exports them under their own keys, and `metric_axes.context` lists `Clinical` and the specific settings the card stores; a card without such rows exports exactly what it did.
  - `summary` is the reference `summarizeDataset` at the all-population lens (§12). A row without an intended-use value (v1.11) adds `(0.5·perf + 0.35·evidence) / 0.85` to the overall average, as D3 does for the score (§4.4).
  - The `ETag` depends only on version, model, and use case, and (v1.10) the local population and its set; an export for a local population carries `population` at the top level and `X-Population` (§21).

## 16. Local-only guard

Added 2026-10-08 (Track A3); tightened 2026-10-13 (security review, see §15 v1.10). The API has no authentication, so every request, read or admin, is refused with 403 `local_only` when:

- the client address is not loopback;
- the `Host` header is not exactly `host[:port]` naming this machine (`localhost`, `127.0.0.1`, `[::1]`; no user info, path, or second colon), which blocks DNS rebinding;
- an `Origin` header is present and is not the request's own origin, `scheme://Host` (default ports normalised). Another page on this machine (for example `http://localhost:3000`) is another origin and is refused, for reads (`GET /admin/assist`) and writes alike;
- the request is not `GET`, `HEAD`, or `OPTIONS` and carries a `Sec-Fetch-Site` header other than `same-origin` or `none`.

Requests without `Origin` (curl, scripts, the tests, Node's `fetch`) are checked by address and `Host` only; no new request header is required. The app's own pages pass because the Vite dev and preview servers proxy `/api` keeping the browser's `Host` (no `changeOrigin`), so the page's `Origin` equals `scheme://Host`; both servers also run with CORS off (`server.cors` and `preview.cors` false), and the API sends no CORS headers, so no other origin can read a response. This holds however the app is started; `python -m app.serve` also binds 127.0.0.1 only.

**The v1.14 interoperability routes (§32, §33)** are behind the same guard: `getCardRecord`, `createEvaluationUpload`, `getEvaluationProposals`, CDS Hooks discovery, and the CDS Hooks service answer this machine only, and still send no CORS headers, so a host application (an EHR test harness, for example) must run on this machine and call them without an `Origin` of its own or through the app's own server. Nothing is opened to other machines or origins for CDS Hooks.

**Request bodies.** Bodies are bounded before they are read: uploads (§11), records uploads (§11.4), study files (§20), narrow model cards, evaluation results files (v1.14, §32.2, 1 MB), and release bundles (§26) by their size limits, `lookup` (§19) and CDS Hooks service (v1.14, §33) bodies at 64 KB (twelve short codes need well under 2 KB), and every other request body (publish, rollback, submissions, the instance, the helper's settings) at 1 MB (added 2026-10-20; their valid bodies are a few hundred bytes). A larger body returns 413 `upload_too_large` (for `lookup`, under its `default` problem response), whether it states a `Content-Length` or arrives chunked.

**No paths.** Problem details and upload reports never contain file-system paths: a missing store returns 503 `store_unavailable` naming the command that builds it, not its location (the server log names it), and an unreadable file is described by its reason only.

**Files (security review 2026-10-13).** Every CSV or XLSX file the API writes (templates, filled or blank, and checked copies of uploads) writes a text value that starts with `=`, `+`, `-`, `@`, a tab, or a carriage return, and is not a plain number, with a leading apostrophe (`'`), so a spreadsheet program shows it as text instead of running it as a formula; XLSX text cells are always string cells, and numbers stay numbers. Uploads drop such a leading apostrophe again, so a downloaded file uploads unchanged, and note every such text value (`formula_like_text`, non-blocking). Before an XLSX upload (§11) or study file (§20) is opened, its zip directory is checked: an upload that would expand to more than 1,024 MB in all or 200 MB in one part other than a worksheet (such as `xl/sharedStrings.xml`), a study file over 100 MB, or any file compressed more than 100:1 (whole file or a part over 1 MB) is refused unopened, as an upload with the blocking issue `unreadable_file` or as 422 `assist_unsupported_input`, with a plain message. (A full filled metrics template expands to about 200 MB at 12:1.)

## 17. Catalogue (v1.6)

Added 2026-10-12. `getCatalogue` (`GET /catalogue`) serves the dashboard's landing page in one request; its tabs, filters, and sorts run in the browser over that response.

- **Tiles.** One per configuration (registry entry × use case, a *card*), in registry order: entries in their registry order, and each entry's use cases in theirs, as `listModels` lists them. `card_id` is `<model_version>|<use_case>`, the id a per-browser profile tracks.
  - `system` is the entry as `listModels` serves it: display name, model name and release, `status`, and the §11.1 entry fields (`kind` always set, `built_on` always a list).
  - `function_category`, `declarations`, `intended_use_defined` (v1.11), and `has_multimorbidity` are those of the configuration in `listModels`. `is_default_use_case` is true for the entry's `default_use_case`.
- **Lens.** Every count is at the all-population lens (All ages, All sexes, All ethnicities) in the first context, `Clinical`, stated in `lens`. Other lenses are the atlas's job.
- **Distributions.** Counts over the depth-1 top-level conditions (`condition_count`, 2,400 on the seed), with exactly the statuses `/metrics/map` and `/metrics/summary` serve at that lens (§4.5). A condition without a row is `no_data` in every view (V1).
  - `overall`: the five statuses. `performance` and `evidence`: `strong`, `moderate`, `weak`, `no_data` (`not_validated`, merged into `no_data` in v1.11, is gone). `intended_use`: `in_scope`, `partially_in_scope`, `out_of_scope` by `intended_use_level`, and `no_data` for no row or (v1.11) no intended-use value; the whole `intended_use` distribution is null for a card without an intended-use statement.
  - Each view's counts sum to `condition_count`. They equal `/metrics/summary` at the same lens and version: its `counts` for overall, performance, and evidence (the statuses a view cannot produce are 0 there), and for intended use its `intended_use_counts` plus `counts.no_data`.
- **Chapters.** Every chapter (level 0) in chapter order, including chapters without conditions (`condition_count` 0, all counts 0), each with the overall distribution of its conditions. They sum to the tile's overall distribution. Where `/metrics/summary` (view `overall`) lists a chapter, its `total` and `counts` equal the tile chapter's `condition_count` and `overall`.
- **Snapshot (v1.11).** The atlas in miniature, one entry per subchapter (block, level 1), in atlas order. To stay within the budget (§10) the subchapters are listed once in the body, `snapshot_blocks: [{id, chapter}]` (block and chapter concept ids), and each tile's `snapshot` holds two arrays aligned with it:
  - `overview`: the block's Overall status at the catalogue lens, the `overall_status` `/metrics/map` serves for the block, except that a rollup without children (`child_count` 0, §6) reads `no_data`, as clients present it (V1). For the population of a population read (§21).
  - `safety`: `serious`, `caution`, or null: the block's safety mark at the catalogue lens, the `safety` column of `/metrics/map` (§18; open and mitigated incidents, closed never count). It does not depend on the population.

  Objects per block (`{id, chapter, overview, safety}` × 225 × 13 tiles) would have added about 230 KB and broken the 300 KB budget; the compact form adds about 55 KB on the demo store. The frontend data client adds `tile.snapshot.blocks = [{id, chapter, overview, safety}]` (`frontend/src/api/apiAdapter.js`, `withSnapshotBlocks`).
- **Last update.** `last_updated` is the newest published version, up to the served one, that changed the configuration, with `at` its publication time (`published_at` in `listVersions`). A version changes a configuration when, compared with the version before it, any of these differ:
  1. the configuration's metrics content set;
  2. its multimorbidity content set (gaining or losing one counts);
  3. its registry signature: the fields the registry change summary compares for the configuration (§11.1), i.e. the entry's display name, model name, release, status, and entry fields, whether this use case is the entry's default and the entry the registry's default, and the configuration's function category, declarations, and (v1.11) intended-use statement; since v1.14 (§28) also the entry's `replaces` and the configuration's record, `performance_measure`, `reference_standard`, and data-protection declarations (so a new `configuration_id` moves `last_updated`; `replaced_by` is derived from other entries and does not);
  4. its safety incidents (v1.7): the incidents of the safety set that name the configuration.
  5. its linked study records (2026-10-21): the records of the version's studies set whose Study ID a row source of the configuration's metrics set names (§11.3, §22: the row's own source or the set's default), compared record by record. So a studies publish or rollback that adds, changes, or removes such a record (a restore that brings one back included) counts for that configuration; one that touches only studies its rows do not name does not.

  The initial import (version 1) changes every configuration it holds, and a configuration that appears later is changed by the version that adds it. So a publish or rollback that puts a different set in place counts, even if the content is equal (re-publishing an unchanged filled template). A registry publish counts only for the configurations whose signature it changes, and a studies publish only for the configurations whose linked records it changes. A prevalence publish never counts, although it can move evidence statuses (the rare-condition penalty, §4.2): the response's `dataset_version` and History show it. The same holds for a population publish or removal (v1.10, §21) and for an effects publish (v1.13, §27). Local results (§26.1) belong to a local population and do not count either. The metrics merge that links rows to a study counts, as every metrics publish does.
- **Safety (v1.7).** `safety` counts the card's incidents over every lens: `serious` and `caution` count the **open** incidents by derived severity (so `serious + caution = open`), and `open`, `mitigated`, and `closed` count every incident by status (§18). A mitigated incident is marked Caution on the atlas but counted only under `mitigated` here. The catalogue's Safety tab sorts and colours by the open counts.
- **Staged reads** work as for every read (§2): the tiles show the staged content. `last_updated` covers published versions only (up to the live version the read is based on). `staged_change` is true for each configuration whose metrics set, multimorbidity set, registry signature, safety incidents, or (2026-10-21) linked study records differ from the live version's, the five things that move `last_updated`; it is always false in live reads.
- **Status filter (run decision R21).** The catalogue's "status" filter uses `system.status`, the registry status `ACTIVE` or `EXPERIMENTAL` (§11). It is not a grading status and not a safety level.
- **Caching.** The body is built once per dataset version (and staged upload) and kept with it, so a response-cache eviction only costs re-encoding; the API builds the live catalogue at startup. Tile distributions are also cached by the content they derive from (metrics set, prevalence set, configuration), so after a publish only the changed configurations are derived again. The version history behind `last_updated` is kept by the API and extended with each publish, so a build reads only the versions published since the previous build. `ETag`, `X-Dataset-Version`, and 304 work as in §2.
- **Notice.** `synthetic_data_notice` repeats `/meta`'s notice, so the page can show it from the one request.
- **Local populations (v1.10, §21).** `population=<id>` serves the tiles for that population: the distributions follow its tiers; registry fields, safety counts, `last_updated`, and `staged_change` do not depend on it. The body names it (`population`). Tile distributions are cached by their content including the population's set.

## 18. Safety incidents (v1.7)

Added 2026-10-12 (§8 items 2 and 5). All incidents are synthetic demonstration data. **Safety incidents never change grades, statuses, warnings, or safeguards.**

- **Data set.** Kind `safety`: one global content set of incidents keyed by `incident_id` (letters, digits, `.`, `_`, `-`; at most 64). Before the first safety publish the store has no safety set and every card has no incidents. Replace and merge uploads, the records upload, staged reads, history, and rollback work as for the other kinds (§11).
- **Fields.** `model_version` and `use_case` name the card, which must be in the live registry or a staged registry upload (`unknown_configuration`; note `configuration_not_published`). `codes`: ICD-11 codes of level-2 concepts as given, each mapped to its depth-1 anchor condition in `condition_ids` (a subcategory counts for its top-level condition); or `chapter_id`, one whole chapter (written `chapter 06` in files), and no codes. A lens (`age`, `sex`, `ethnicity`; an empty cell is `All …`). `incident_type`: `harmful_recommendation`, `fabricated_content`, `subgroup_bias`, `performance_drift`, `developer_notice_or_recall`, `other` (readable labels: Harmful or incorrect recommendation, Fabricated content, Subgroup bias, Performance drift, Developer notice or recall, Other). `harm`: `occurred`, `possible`, `none`. `status`: `open`, `mitigated`, `closed`. `source_type`: `study`, `incident_report`, `developer_notice`; `source_reference` (required); `study_id` (required for a study). `reported_date`, `updated_date` (optional, not before the reported date), and a synthetic `summary` of at most 280 characters.
- **Severity** (derived, never stored): **`serious`** = status open and (harm occurred or possible, or type `developer_notice_or_recall`); **`caution`** = any other open incident, or a mitigated one; a closed incident has none (listed, not coloured).
- **Lens rule.** An incident applies to a requested lens when, on each axis, its value is `All …`, equals the requested value, or the request is `All …` on that axis.
- **Marks.** A condition's safety mark at a lens is the worst severity (`serious` > `caution`) of the incidents that apply to it, or null. A deeper category takes its anchor's mark; a block or chapter the worst mark of its depth-1 conditions. `getMetricMap` serves it in the `safety` column, and the multimorbidity display map likewise for the concepts it lists.
- **Concept reads.** `getConceptMetrics` lists in `incidents` every incident that applies at the lens, closed ones included, newest first (by updated, else reported date; then incident id), each with its derived `severity`; a rollup lists those of its conditions, a deeper category its anchor's.
- **Summary.** `getMetricSummary` with `view=safety` counts the depth-1 conditions by mark: `serious`, `caution`, and `none` (§14).
- **Catalogue.** Each tile's `safety` counts the card's open incidents by severity and all its incidents by status, over every lens (§17); its `snapshot.safety` gives each subchapter's mark at the catalogue lens (v1.11).
- **Incident list (v1.11).** `listIncidents` (`GET /admin/safety/incidents`, tag `admin`, never cached) serves `{dataset_version, incidents}`: every stored incident of the version (open, mitigated, and closed), newest first (by updated, else reported date; then incident id), each a `StoredIncident`: the `SafetyIncident` fields plus `code_names` (the preferred term of each code, aligned with `codes`; null for a code the atlas lacks) and `chapter_no` (the two-digit number of `chapter_id`, or null), which the Data Library's incident form shows. Optional `model` (an AI system's incidents) and `use_case` filters; a filter that matches nothing gives an empty list, not 404. It takes `version=staged:<upload_id>` like every read (§2). Editing an incident is a merge upload of the changed record (§11.2); a closed incident can be changed and reopened like any other.
- **Public incident list (v1.14, §30).** `listSafetyIncidents` (`GET /incidents`, tag `meta`) serves the same body as `listIncidents` for the same `model`, `use_case`, and `version` (every incident of the version, open, mitigated, and closed, newest first, as `StoredIncident`), as a public read with `X-Dataset-Version`, an ETag, and 304s. It lets a card's readers see its incidents over time (the Regulator summary, §30) without the admin operation. A filter that matches nothing gives an empty list, not 404; a store without a safety set gives an empty list.

## 19. Lookup: the live interaction plugin (v1.8)

Added 2026-10-12. `lookup` (`POST /lookup`) answers, for one card, a few ICD-11 codes, and a coarse population, what the atlas card shows for each condition. The in-app demo page and the embeddable panel (`<bmc-live-panel>`) are its clients. All data is synthetic; **this is a demonstration, not clinical decision support, and must not be used for clinical decisions** (K10). The response says so in `disclaimer` ("Demonstration on synthetic data. Not for clinical use.") and repeats `/meta`'s `synthetic_data_notice`.

- **Request.** JSON shaped like a CDS Hooks context, so an EHR integration can follow later (D11; not part of this run):
  - `hook` (optional): `broad-modelcard-lookup`.
  - `context.card`: `model_version` and `use_case` (a card, §Vocabulary). An unknown model or a use case the model lacks returns 404 `unknown_model` / `unknown_use_case`, after body validation (422 before 404, §3), with a detail that names the field only ("Unknown AI system." / "Unknown function for this AI system."), never the name sent.
  - `context.conditions`: 1 to 12 codings `{system?, code}` (422 `invalid_selection` otherwise). `system`, if given, is `http://id.who.int/icd/release/11/mms`; `code` is letters, digits, and dots, at most 16 characters (422 `invalid_selection` otherwise), so no free text fits.
  - `context.population` (optional; null or absent values mean the whole population on that axis): `age_group` `0-17`, `18-39`, `40-64`, `65+` → `Age 0-17` … `Age 65+`; `sex` `female`, `male` → `Sex Female`, `Sex Male`; `ethnicity` `white`, `black`, `hispanic`, `asian`, `other` → `Ethnicity White` … `Ethnicity Other`. Other values return 422 `invalid_lens`.
  - `context.setting` (optional, v1.14, §29): a care setting's code, `emergency_department`, `intensive_care`, `inpatient_ward`, `outpatient_clinic`, or `primary_care` (the first five study setting categories); null or absent means any setting (`Clinical`). Other values return 422 `invalid_lens`, naming the field only. Each condition then reads what `getConceptMetrics` serves at that setting (No data where the card stores none), the response's `lens.context` names the setting, and every link ends its lens part with `setting=<code>`.
  - **Closed:** an unknown key anywhere in the body (top level, context, card, a coding, population) returns 422 `invalid_parameter`, so identifiers, names, dates, notes, or tokens cannot be sent along.
  - `context.population_id` (optional, v1.10): a local population from `/meta` `populations` (§21); absent or null means the default population. Not to be confused with `context.population`, the coarse demographic lens. An unknown id returns 404 `unknown_population` with the detail "Unknown population_id." (never the value sent); a malformed one 422 `invalid_parameter`. The response then carries `population` and `X-Population`.
  - `version` is the query parameter of every read (`live` or `staged:<upload_id>`, §2).
- **Matching.** A code matches the level-2 concept whose `icd11_code` equals it, ignoring case (§5: deeper categories included). A code that matches no level-2 concept (an unknown code, a chapter number) is listed as `{code, matched: false}`, not an error. `conditions` has one entry per code, in request order, with the code as sent.
- **Per matched condition** (`LookupCondition`), exactly what `getConceptMetrics` serves for the concept at the lens and version: `statuses` (`overall`, `performance`, `evidence` from `metrics.status`, `intended_use` from `metrics.intended_use_level`), `warnings`, `safeguards`, `incidents`, and `provenance` (with `lens_fallback` and `data_source`), plus `safety`, the concept's safety mark as `/metrics/map` serves it (§18). A deeper category serves its anchor's row (§5); `anchor_id` names that depth-1 condition (the concept's own id at depth 1). A condition without a row at the lens has statuses `no_data`, `intended_use` null, empty warnings and safeguards, and `provenance` null, and is drawn as **No data** like on the atlas (§4.5, V1); its incidents still apply.
- **Combination.** When the matched codes name at least two distinct conditions (as depth-1 anchors, §8) and the card stores exactly that combination, `combination` holds its key, `label`, `concept_ids` (the anchors in request order), the statuses, warnings, safeguards, and provenance that `getMultimorbidityCombination` serves at the lens, `safety` (the worst mark of its conditions), and a link. Otherwise `combination` is null: a combination is never inferred from its parts or from a stored subset.
- **Links.** `card.card_url`, each condition's `card_url`, and the combination's `card_url` are relative to the frontend root (`atlas.html?…`) and use the atlas URL parameters of `frontend/src/app/startupParams.js` (`version`, `model`, `use_case`, `view`, `age`, `sex`, `ethnicity`, `population`, `mode`, `depth`, `chapter`, `concept`, `selected`), in its order and encoding (`URLSearchParams`, with commas and colons left readable), except that `population` comes last (below). `depth` is never written, so the atlas opens a lookup link at its mode's default explanation depth. "All …" lens values are left out; `version` appears only for a staged read. Every link names `view=overall`, the view of the statuses it reports: a link that carries atlas state (any parameter besides `model` and `use_case`) opens exactly what it names for every reader, and the atlas applies a reader's own defaults (lens, depth, local population) only to links that name at most the card, so a lookup link opens the figures it reports, under the default prevalence unless it names a population. For a local population (v1.10) every link ends with `population=<id>`, so the atlas opens the same population once it reads that parameter (frontend track S6f). A condition links with `concept=<concept_id>` (and `chapter=<chapter_id>` for a deeper category, which the atlas only knows once its chapter is open); the combination with `mode=multimorbidity&selected=<ids>`.
- **Privacy.** The lookup request travels in the POST body, never in a URL, so the lookup itself never reaches an access log. Nothing of the request or the response is stored, cached, or logged: the response is built from the per-concept derivations the atlas reads already cache (keyed by concept and lens), is not kept in the response cache, and carries `Cache-Control: no-store` and `X-Dataset-Version` (no `ETag`). Problem details name the field, never the value sent. The route handles every error it meets while answering (an unknown version or card, a data error, an unexpected error), so none reaches the server's own error logging; an unexpected one is logged by its type only, without a traceback or message. Nothing from the request body is logged. Tests assert that no part of a request body appears in the log output (`tests/test_lookup.py`, `tests/lookupClient.test.js`). **Following a link is ordinary atlas use and is not covered by this.** Every `card_url` names the case's conditions (`concept`, `chapter`, `selected`) and population (`age`, `sex`, `ethnicity`, `population`) in the page URL, so once a reader opens one, they appear in the browser's address bar and history, and in the atlas's own read requests (`GET` query parameters), which a local access log (for example the server's request log) may record, exactly as when the reader picks the same condition on the atlas by hand. The links carry no identifiers, names, dates, or free text (the request is closed, see Request).
- **Local only.** The local-only guard (§16) applies: a host page must be served from this machine (`localhost`, `127.0.0.1`), and the API sends no CORS headers, so the embedding page must be same-origin with the API (served through the app's dev or preview server, which proxies `/api`). The API is not reachable from another application or machine, and no EHR integration exists in this prototype.

## 20. Assisted data entry (v1.9)

Added 2026-10-12 (§8 item 6). An optional helper turns one study into **proposed** records for the `metrics` or `safety` data set. **It proposes, never publishes:** `proposeRecords` writes nothing (no upload, no version); the maintainer accepts the records they keep by sending them to `createRecordsUpload` (§11.4), which stages a merge upload, and the normal check → change summary → preview → publish flow follows (§11, §11.2). With the helper off, every other operation works unchanged.

- **Providers** (one backend module, `app/assist/`; plain HTTP from the standard library, no SDK, no PDF library):
  - `hosted`: the Anthropic Messages API (`POST https://api.anthropic.com/v1/messages`, headers `x-api-key` and `anthropic-version: 2023-06-01`) with the maintainer's own API key. Default model `claude-sonnet-5-5` (configurable). A PDF is sent as a base64 `document` block; text and tables as text. Optional `base_url` for a gateway: https, or http on this machine only.
  - `local`: an OpenAI-compatible endpoint on this machine (`POST <base_url>/chat/completions`, e.g. `http://127.0.0.1:11434/v1`), text and tables only; an optional bearer key. The base URL must name a loopback host (`127.0.0.1`, `::1`, or `localhost`; otherwise 422 `invalid_parameter`), so studies and keys stay on this machine unless the maintainer chooses the hosted provider. A stored configuration with another host is ignored. A PDF to a local model returns 422 `assist_unsupported_input` ("paste the text") before anything is sent.
- **Configuration.** `configureAssist` takes `{provider, model?, base_url?, api_key?}`; it is validated (422 `invalid_parameter`) and stored on the backend machine in one JSON file with mode 600: `backend/data/assist.json` for the live store, `<store name>.assist.json` next to any other store (so the demo and scratch stores never share the live store's key), or `$BMC_ASSIST_CONFIG`; all are ignored by git. A request without `api_key` keeps the stored key only when the provider and the origin (scheme, host, and port) of its endpoint stay the same, so a stored key is never sent to an address it was not saved for; a path change on the same origin keeps it. Otherwise the stored key is dropped: a hosted model then needs `api_key` again (422 saying the address changed), and a local model is saved without a key. A hosted model always needs one. Nothing is sent to the provider on configure. `clearAssist` deletes the file (204).
- **The API key is write-only.** No response carries it (`AssistStatus.key_set` says whether one is stored); it never enters the store, uploads, annotated files, templates, exports, or logs, and is removed from every problem text. Problem details of the assist operations never repeat the key or the study (validation problems name the field, not the value, as for `lookup`, §19), and an unexpected error is logged by its type only. A provider failure is logged in the helper's own words ("The provider answered HTTP 500."); the provider's message text appears only in the redacted problem detail, never in the log. Redirects from the provider are not followed (they would carry the key elsewhere). Tests use a canary key and assert its absence from every response, log record, the SQLite files, and the uploads folder (`tests/test_assist.py`).
- **What leaves the machine, and when** (`AssistStatus.privacy`). Only on `proposeRecords`, and only to the configured provider: the submitted study, the helper's instructions, the list of cards (model version, function, display name), the lens values, and, for a hosted model, the results of its condition searches (codes and names from the atlas). Nothing else: no store content beyond those, no other uploads, no key to any other host. Studies must be synthetic or published text; never patient data.
- **Input.** Exactly one of `file` (PDF, `.txt`, `.md`, `.csv`, `.tsv`, `.xlsx`; at most 10 MB, 413 `upload_too_large`; other types 415 `unsupported_file_type`) or `text` (at most 200,000 characters), plus `kind` (`metrics` or `safety`) and an optional card (`model_version` with `use_case`; 422 if only one is given or the card has no metrics). Tables are sent as text with their row numbers so values can be cited by row and column. Files are read row by row and capped: at most 2,000 rows and 100 columns per table or sheet, 20 sheets, and, as for pasted text, 200,000 characters of text from any file; the text sent then ends with a line saying it continues, and `AssistInput.truncated` (optional, absent means false) is true. A table the reader cannot parse (for example a CSV cell longer than 131,072 characters, or a workbook whose rows cannot be read) is 422 `assist_unsupported_input`. The response identifies the input by `media`, `bytes`, `sha256`, file name, and `truncated`, never by its content.
- **Codes and cards come from the store.** A hosted model calls the backend search (§9) as the tool `search_conditions` (at most 8 requests per proposal). For a local model the backend resolves conditions named without a code after the answer: an exact name match in the atlas, otherwise the model chooses among the atlas's search candidates in a second request. A code the model gives that the atlas does not have is **dropped** (`unknown_code`), never replaced; a subcategory, block, or chapter given for metrics is dropped as `not_a_condition` with its top-level condition named; an unknown card is `unknown_card`; a record for another card than the one chosen is `other_card`; an unknown lens value is `invalid_value`; a repeated record is `duplicate`. Each dropped item lists what the model proposed and its source.
- **Records.** `batches` group the records as `createRecordsUpload` takes them: per card for metrics (`model_version`, `use_case`), one batch for safety (each incident names its card). Each record's `record` holds exactly the template keys of that data set (§11), with readable labels; `fields` give per key the `origin` (`study`: stated in the study; `store`: a metrics field the study does not state, kept from the stored row, because a merge row replaces the whole row, §11.2; a field the model gave whose value does not parse stays `study`, empty, and flagged, never filled from the stored row; `search`: a code resolved by name; `request`: the chosen card; `default`: an "All …" lens value or an empty optional field; `generated`: a safety incident id `AST-<input hash>-<n>`), the `source` (`quote`, `location`: page, paragraph, or row and column), the model's `confidence`, and `uncertain` with a `reason`. A field is uncertain when the model says so, when it has no source quote, when its quote is not words of the study as the helper read it (pasted text, CSV, or XLSX; compared ignoring case, spacing, and punctuation: "This quote is not in the study as read; check the value against the study."; a PDF's quotes cannot be checked, since the backend does not read PDF text), when a value was converted (a percentage) or is outside its range or list, when a code was matched by name among candidates, or when a value the check requires is missing (Source, Study, and Source date of a metrics merge row; required incident fields). A metrics record that keeps study-reported values from the stored row (origin `store` on `perf`, the CI bounds, the evidence grade, the counts, or the validation type; intended use and warnings describe the card and do not count) while its Source, Study, or Source date come from the study has its `source` field flagged ("Some values come from the stored row, not this study; the whole row will be credited to this study."): a merge row has one source, so staging credits every value of the row to this study, and the maintainer decides whether to keep, edit, or untick it. Uncertain values are proposed as they are and flagged; the check reports what does not validate after acceptance. A number that is not a finite number (text such as `nan` or `inf`, or a JSON NaN or infinity) is proposed empty and flagged "Not a number.", a non-finite `confidence` is null, and such a value in a dropped item is null.
- **Errors.** 409 `assist_not_configured` while the helper is off (the detail says how to enable it); 502 `assist_provider_error` when the provider cannot be reached, answers with an error or a redirect, declines, runs out of length, or does not answer with the requested JSON, or does not finish in time: one proposal has 180 seconds in total across all its requests (the hosted tool loop, the local chooser), and each request waits at most what is left. 409 `assist_busy` while another proposal is running: the helper reads one study at a time, and a request the maintainer cancelled keeps running until the provider answers or the 180 seconds pass, so a retry waits instead of piling up.
- **Evaluation.** A fixed synthetic study set (`backend/assist_eval/`, seven excerpts in text and CSV with expected records) and `python -m app.assist.evaluate --provider fake|hosted|local` measure field-level accuracy, record recall and precision, expected drops, uncertainty flags, codes in the store, and sourced fields (backend/README.md). The fake provider (canned answers) runs in the tests; the accuracy of a real model is measured by running the command with a configured provider.
- **Search rewrite (v1.14, §31).** When the helper is configured, `interpretQueryWithHelper` (`POST /assist/interpret`) asks the same provider to read one search query as chips. **Only the query text and the vocabularies** (AI system model versions and display names, function names, the age, sex, and ethnicity values, the care settings) are sent, in one request without tools (`max_tokens` 1,000; 30 seconds in all); no results, store content, or study. The backend checks every chip it gets back (§31) and returns `provider`, `model`, and the `dropped` chips. 409 `assist_not_configured` while the helper is off; 502 `assist_provider_error` as for proposals; the key is never sent anywhere else and never appears in a response or the log, and the query is not logged. `AssistStatus.privacy` says so. The atlas offers **Ask with the helper** only while `getAssistStatus` says the helper is on.
- **Local only.** The local-only guard (§16) applies to all four operations and to the search rewrite; the backend still binds 127.0.0.1, and its only outbound requests are the configured provider's.

## 21. Local populations (v1.10)

Added 2026-10-12 (§8 item 8). A **local population** is a named local prevalence set, e.g. "Northbridge region (fictional)": commonness tiers for the conditions of one region or service. A reader switches to it for a request; the default population (the `prevalence` data set) stays the shared baseline. Only local prevalence is covered; a local demographic mix (lens weights) is deferred. All data is synthetic.

- **Overlay.** A population lists tiers for some ICD-11 codes of level-2 concepts. For a read that names it, each listed concept takes the population's tier and score (§5, same score table and clamp as the default set); every other concept keeps the default tier. A change to the default prevalence therefore shows through for the codes a population does not list.
- **Same formulas (D14).** The population's scores feed exactly the existing derivations: the evidence-grade penalty (§4.2), rollup weights and the rollup's evidence grade (§6), block and chapter prevalence (§5), the concepts' `prevalence_tier` and `prevalence_score` (and so the frontend's atlas layout, §13), and every status derived from them (§4.4, §4.5). No formula, threshold, or band changes. A test shows that reading with a population equals publishing its tiers as the default prevalence (`tests/test_populations.py`).
- **Reads.** `population=<id>` (pattern `^[a-z0-9][a-z0-9-]{0,39}$`) is accepted by every read that depends on prevalence: `getCatalogue`, `getAtlasOverview`, `getChapter`, `getMetricMap`, `getMetricSummary`, `getConceptMetrics`, `getMultimorbidityCandidates`, `getMultimorbidityCombination`, `searchConcepts` (its concept records carry tiers), `exportConcept`, `exportDataset`, and the `lookup` body as `context.population_id` (§19). `getMeta` and `listModels` take none: they describe the version; `/meta`'s chapter records carry the default prevalence. An id the version does not hold returns 404 `unknown_population`; a malformed one 422 `invalid_parameter`.
- **Naming the population.** A population response carries `population: {id, name}` in its body (the dataset export at its top level) and the header `X-Population: <id>`. A default response carries neither, so its body and ETag are byte for byte what they were before populations existed; a test compares a fixed set of reads before and after a population is published and removed (`tests/test_populations.py`). Every view that uses a population must name it next to the synthetic-data notice (frontend).
- **Caching.** ETags, the response cache, the per-version contexts, and the catalogue's tile cache are keyed by the population id and its content set as well as the version (§2), so default and local answers never mix and a replaced population never serves stale answers. A population context is built on its first read (about 0.1 s on the demo store) and kept for the most recent few.
- **Staged reads.** `version=staged:<upload_id>` and `population` combine: the population is looked up in the staged version. A staged upload of another kind is read for a live population; a staged **population** upload adds or replaces its own population in its staged version, so it is previewed with `version=staged:<upload_id>&population=<its id>`. Without `population` such a staged read answers like the default. A population the staged version lacks is 404 `unknown_population`.
- **`/meta` `populations`.** Each population of the version, by id: `id`, `name`, `codes` (how many codes it lists), and `updated_version` (the newest version up to the served one that put its current set in place: its publish, a replacement, or a rollback that restored it; null for a staged set). Always sent, empty when there are none.
- **Data set `population`.** One content set per population id (stored like a prevalence set, with the name in `population_sets`; migration `0005`). Its template is the prevalence template (ICD-11 code, Condition, Commonness, and the optional Action, Source, Study, Source date); the population is chosen at upload with `population_id` and `population_name` (at most 80 characters; required for a new population, else the live name is kept), shown in `Upload.target`. Uploads are replace only (`mode=merge` returns 422): a publish adds the population or replaces its whole list. One staged upload per population id. A filled template with `population_id` returns that population's rows; without it, the default tiers to edit into a new population.
- **Aggregate data only.** The check rejects anything that looks patient-level with the error `patient_level_data` and a plain fix: an extra column whose header names identifiers, names, birth or contact details, encounters, or per-person values (e.g. Patient ID, Date of birth, Visits per patient), and a code given on more than one row (a list of patients or cases looks like that). Other extra columns are `extra_column` as for every template. Such a file is not kept: it is deleted, with everything kept beside it, as soon as its check ends. The upload stays `invalid` with its problems; its report keeps the examples of `patient_level_data` (a column header or an ICD-11 code) but none of other problems, which would quote cells of the file; `downloadAnnotatedUpload` answers 409 `upload_not_staged` with a plain message, and the Data Library offers no marked copy. Patient-level or real patient data must never be uploaded.
- **Change summary.** Rows compare the staged population with the live set of the same id (none for a new one), by code, with source changes counted (§11.3). Status shifts compare the default answers with the answers for the staged population, for every model and use case at the all-population lens, as for prevalence (§11); they are computed even when the rows equal the live population's. The version summary says "Local population <name> (<id>): …, N overall status changes against the default population."
- **Removal.** `removePopulation` (`POST /admin/populations/{population_id}/remove`, optional body `{note}` as for rollback, §11.5) publishes a new version (kind `population`, summary "Removed the local population <name> (<id>).") that lists every set of the live version except that population's. It is serialized like a publish (409 `publish_in_progress`); an id the live version lacks is 404 `unknown_population`. History keeps the population: a rollback of kind `population` to an earlier version restores the populations as they were then. Replacing a population with an empty file is not a removal (an empty file is invalid).
- **History and catalogue.** A population publish, replacement, or removal is a version of kind `population`. It never moves a catalogue tile's `last_updated` (§17), like a prevalence publish.

## 22. Studies and appraisal (v1.13)

Added 2026-10-20 (release 0.4). A **study record** describes one study behind metric rows, so the evidence grade can take the study's quality into account and a reader can open the appraisal behind it. All studies are synthetic demonstration data with fictional names.

- **Data set.** Kind `studies`: one global content set of records keyed by `study_id` (letters, digits, `.`, `_`, `-`; at most 64), like `safety` (§18). Before the first studies publish the store has no studies set, and no row links. Replace and merge uploads (§11.2: an empty Action adds or replaces a record, `Remove` deletes it; there is no older-study rule), the records upload (§11.4; the Data Library's one-study form uses it), staged reads, history, and rollback work as for the other kinds. Stored in the table `studies` (migration `0007`); later phases may add optional effect records (their own table) and a study scope or population (nullable columns) without changing this one.
- **Fields** (template columns in parentheses; readable labels and codes are both accepted):
  - `study_id` (Study ID), `title` (Title, at most 200 characters), `design` (Design): `vignette`, `simulation`, `benchmark`, `retrospective`, `prospective`, `real_world_deployment`, `randomized_trial`.
  - `setting` (Setting, free text, at most 280, e.g. "Emergency department, tertiary hospital"), `sites` (whole number ≥ 1), `patients` (Patients: patients or cases, whole number ≥ 0; aggregate counts only), `peer_reviewed` (Yes/No), `conducted_by` (Conducted by): `developer`, `independent`, `hospital`.
  - `reporting_guideline` (Reporting guideline): `none`, `tripod_ai` (TRIPOD+AI), `stard_ai` (STARD-AI), `consort_ai` (CONSORT-AI), `decide_ai` (DECIDE-AI), `other`; `guideline_followed` (Guideline followed): `yes`, `partly`, `no`, required unless the guideline is `none`, and empty (null) when it is.
  - `risk_of_bias` (Risk of bias): `low`, `some_concerns`, `high`, `unclear`, the overall judgement (for example with PROBAST+AI); `risk_of_bias_notes` (optional free text, at most 500, e.g. per-domain notes).
  - `population` and `evaluation_conditions` (free text, at most 280 and 500), `model_version` (Model version evaluated, optional; when given it must be an AI system of the live registry, or of a staged registry upload, which is a note), `publication_date` (YYYY-MM-DD), `source_url` (Source URL, optional, `http://` or `https://`).
  - Optional since **v1.14** (migration `0012`), each column optional in the template, so files without it stay valid:
    - `applicability` (Applicability concerns): `low`, `high`, `unclear`, the overall judgement of how well the study's patients, setting, and outcome match the intended use (PROBAST+AI style), and `applicability_notes` (Applicability notes, at most 500).
    - `quality_tool` (Appraisal tool): `probast_ai` (PROBAST+AI), `appraise_ai` (APPRAISE-AI), `quadas_ai` (QUADAS-AI), `other`; `quality_score` (Appraisal score): a number from 0 to 100 for a tool that scores, and only with a tool. Served as a whole number when it has no decimal part (72, not 72.0).
    - `setting_category` (Setting category): `emergency_department`, `intensive_care`, `inpatient_ward`, `outpatient_clinic`, `primary_care`, `mixed`, beside the free-text `setting`. The first five are the specific settings a later care-setting lens uses.
    - `configuration_id` (Configuration evaluated): the configuration of the AI system the study evaluated, as a label (letters, digits, `.`, `_`, `-`; at most 64). It is **not** checked against the registry as an error; since v1.14 (Q4) one its AI system's cards do not list is the note `configuration_not_in_registry`, and it drives the evidence age (§28.5).
    - **Serialization:** each is sent only when stored and never as null (unlike the older optional fields, which are always sent), so a study without them has exactly its v1.13 keys and every response that embeds it (`listStudies`, `getStudy`, `Appraisal.study`, `Effect.study`, comparison card facts, exports) is byte for byte unchanged.
    - **Not graded**: none of them changes a grade, signal, adjustment, status, warning, score, comparison flag, or summary; `tests/test_study_fields.py` publishes them on a linked study and finds every graded read byte-identical.
- **Validation** (blocking errors, each with a plain fix): `missing_value`, `invalid_value` (a malformed Study ID, a text too long or with a line break), `unknown_applicability`, `unknown_quality_tool`, `quality_score_without_tool`, `unknown_setting_category`, `invalid_study_configuration` (v1.14; a score outside 0–100 is `out_of_range`, one that is not a number `not_a_number`), `unknown_study_design`, `unknown_study_conductor`, `unknown_reporting_guideline`, `unknown_guideline_followed`, `missing_guideline_followed`, `guideline_followed_without_guideline`, `unknown_risk_of_bias`, `out_of_range` (sites below 1), `not_a_whole_number`, `invalid_date`, `invalid_url`, `unknown_study_model`, `duplicate_key`. Notes: `model_not_published`, `configuration_not_in_registry` (v1.14, Q4: a study that names its AI system names a Configuration evaluated that none of that system's cards lists, in the live registry or a staged registry upload; often an earlier configuration, which the condition card then names as such, §28.5), `nothing_to_remove`, `formula_like_text`. Staged studies uploads are checked again after a registry publish or a rollback.
- **Link.** A stored metrics row (§11.3) links to a study when its row source's `study` (the Study column of its upload) **equals a `study_id` of the version's studies set exactly** (case and spacing included). The link is not stored: it follows from the row source and the studies set of the version read, so publishing, changing, or removing a study record re-links or unlinks rows without touching them, and a staged studies upload previews its effect. Free-text studies stay allowed: a metrics upload whose Study names no record stays valid, and its check adds one note `unknown_study` per such Study value (with the number of rows and the first row). Multimorbidity rows have no row source and never link; safety incidents' `study_id` does not link either.
- **Grading (D5; §4.2).** For a linked row the evidence signal adds, with the penalties and before the final clamp to 0–1:
  - **+0.05** when the reporting guideline was followed (`guideline_followed` `yes`; `partly`, `no`, and `none` add 0);
  - **−0.10** for risk of bias `high`, **−0.04** for `some_concerns` or `unclear`, 0 for `low`.

  The grade cut-offs are unchanged, and the adjustment enters only a derived signal: a row whose stored grade is served (§4.1, samples or studies missing) or that has no evidence is unchanged. A row without a linked study adds nothing, so every read is byte-identical to before for such rows; a store without studies answers every read exactly as v1.12 did, apart from `/meta`'s two constant fields below (`tests/test_studies.py` compares a fixed set of reads on the seed store before a studies publish that links no row, after it, and after restoring it away).
- **Aggregates.** A rollup (§6) adds the prevalence-weighted mean of its children's adjustments (the rollup weights; a child without a link counts 0); a lens fallback over several rows (§7) adds the unweighted mean of its rows' adjustments; a lens fallback that finds one row serves that row as stored, adjustment included. When no row links a study the mean is exactly 0 and nothing changes.
- **Published constants.** `/meta.evidence_signal_weights` (`type` 0.33, `studies` 0.17, `sites` 0.12, `peer` 0.18, `size` 0.20) and `/meta.evidence_study_adjustments` (`guideline_followed` 0.05; `risk_of_bias` `low` 0, `some_concerns` −0.04, `high` −0.10, `unclear` −0.04), so the frontend explains a signal without restating them.
- **Appraisal.** `getConceptMetrics` and `exportConcept` add `appraisal` to the served `MetricRow` when a linked study enters it, and leave it out otherwise (so unlinked rows keep their exact shape):
  - A **stored row** at the requested lens (a condition, or a deeper category through its anchor) linked to a study: `study` (the `Study` record), `study_adjustment` (guideline plus risk-of-bias adjustment, 4 decimals), `applied` (whether the row's signal is derived and so includes it), and `terms` when applied: the five term scores of §4.2 (`type`, `studies`, `sites`, `peer`, `size`, each 0–1, weights in `/meta`), `base_signal` (their weighted sum clamped to 0–1), `penalties` (the sum of the §4.2 penalties that apply, 0 or negative, computed with the prevalence and chapter of the row's condition, the anchor for a deeper category), `guideline_adjustment`, `risk_of_bias_adjustment`, `signal` (the served `evidence_signal`), and `grade`. The terms other than `signal` are rounded to 4 decimals; `base_signal + penalties + both adjustments`, clamped to 0–1, is the signal.
  - An **aggregated row** (rollup, lens fallback) whose mean adjustment is not 0: `study` null, `study_adjustment` (the mean), `applied`, and `terms` null.
  - The dataset export (`exportDataset`) and the other reads serve the adjusted grades but no `appraisal`.
- **Not appraised, made visible (2026-10-21; grading unchanged).** A row without a linked study keeps its grade; the map and the summary say where a grade rests on a study record, so readers can see the absence of an appraisal where they compare:
  - `getMetricMap` adds `appraisal`, an array aligned with `rows` like `mapping` and `layer`: `linked` for a condition (or a deeper category, through its anchor) whose result rests on a stored row linked to a study record (its own row, a local row for a population with local results, or, for a lens fallback over several rows, at least one of them), `includes_linked` for a result that aggregates conditions (a block, a chapter, or in another ontology a condition mapped to an ICD-11 block) at least one of which is linked, else null. Another ontology follows the ICD-11 condition a concept serves (§23.3).
  - `getMetricSummary` adds `appraisal_counts` `{graded, linked}` on every view: the depth-1 conditions with an evidence grade at the lens, and how many of them are linked.
  - **Both are sent only when at least one row of the answer is linked** (the summary: one graded condition). So every read of a store without studies, of a card whose rows name no study record, and of a lens or chapter where none is linked stays byte for byte what it was; the guarantees above, §23.3's, and §26.1's are unchanged (`tests/test_appraisal_marks.py`). An absent array means every row is null. They are keyed and cached with the answer they belong to, and the static demo records them with it.
  - The frontend draws **Not appraised**, a secondary marker that never replaces the evidence status (§13), on the Evidence view's graded conditions and subchapters whose `appraisal` is null, explains it in the legend, and names the counts in the Summary; the condition card keeps "No study record linked".
- **Reads.** `listStudies` (`GET /studies`, tag `studies`) serves `{dataset_version, studies}`: the records of the version in stored order, optionally only those whose `model_version` equals `model` (a filter that matches nothing gives an empty list, not 404). `getStudy` (`GET /studies/{study_id}`) serves `{dataset_version, study}`; an id the version lacks is 404 `unknown_study`, a malformed one 422. Both take `version` (live or staged, §2), carry `X-Dataset-Version` and an `ETag`, take no `population`, and stay far below the §10 budgets (seven demo records are about 6 KB). The static demo records both whole.
- **Change summary (§11).** Rows compare the staged set with the live one by study id (added, changed, removed; a merge's `unchanged` counts the records it touched); samples name `<study_id>: <title>`. Status shifts compare every card whose metrics set links a study in the live or the staged version (other cards cannot shift) at the all-population lens, like prevalence. The version summary reads "Studies: N studies added, …, M overall status changes."
- **Catalogue (§17).** Since 2026-10-21 a studies publish or rollback that adds, changes, or removes a study record a card's stored rows name moves that card's `last_updated` (§17, item 5): its grades may have changed with it. Cards whose rows name none of the changed records do not move, nor do prevalence, population, or effects publishes. Tile distributions are cached with the studies set when a card links one, so they follow it. The metrics merge that links rows to a study is a metrics publish and moves the card's `last_updated` as usual.
- **Frontend.** The condition card keeps the simple status and grade and offers "How was this assessed?" (plain words at plain depth; the terms and `/meta` weights at expert depth) and a separate "Study quality" section about the underlying study (risk of bias, guideline, who conducted it), kept apart from any population or subgroup result. Without `appraisal` it says that no study record is linked. Since v1.14 Study quality shows applicability concerns as a line of its own beside risk of bias, the appraisal tool and its score ("APPRAISE-AI score 72 of 100"), and the setting category and configuration evaluated as study facts; applicability notes at expert depth. A field that is not stated is left out.

## 23. Ontologies (v1.13)

Added 2026-10-20. ICD-11 is the standard: it is the default of every read and the storage key of every result, population, incident, and combination, and uploads stay in ICD-11 codes. **ICD-10-CM** and **MONDO** are alternative hierarchies a reader can choose: they are *projected* over ICD-11 through an explicit crosswalk, never stored with results of their own (D1). All results stay synthetic demonstration data.

- **Sources and import.** The pinned releases are in `scripts/ontologies/sources.json` (MONDO `mondo.obo` v2026-10-06, CC BY 4.0; ICD-10-CM FY2027 tabular, US CDC NCHS, public domain; WHO ICD-10 → ICD-11 mapping tables 2026-01, CC BY-ND 3.0 IGO, the same ICD-11 release as the seed). `npm run ontologies:fetch` downloads them into `backend/data/ontology-sources/<id>/` (gitignored), keeping files that already match their pinned size and SHA-256; `npm run ontologies:import` (`app.ontologies.importer`, run with `python -I`) checks every file against the manifest, then replaces each ontology's rows in the store at `BMC_DB` in one transaction (idempotent; a missing file stops it with the fetch command, a changed one with "fetch it again"). `npm run demo:build` imports them last when they are downloaded and otherwise prints a notice. No source file and nothing derived from the WHO tables is committed: the WHO tables are read unmodified at import time, and the derived tables exist only in a local store. The parsers use the Python standard library only and treat the files as untrusted (archive members are size- and ratio-checked before they are read; XML that declares a document type or entities is refused).
- **Store** (migration `0008`): `ontologies` (id, name, release, licence, attribution, the pinned sources read, counts), `ontology_concepts` (the atlas shape: `concept_id`, `parent_id`, level 0 chapter, 1 block, 2 condition, `chapter_id`, two-digit `chapter_no`, `block_id`, the ontology's own `code`, `pt`, `fsn`, `sort_order`, `depth_in_kind`, `metric_anchor_id`, and every parent the import holds), and `ontology_mappings` (one row per level-2 concept, below). They are reference data like `concepts`: no publish, rollback, or upload touches them. A backend keeps the ontologies it loaded until it restarts; `npm run ontologies:import` ends with a line saying so (2026-10-21), and `npm run demo:build` refuses to build a store a running backend has open.
- **Synonyms (v1.14, §31).** The same import writes the synonyms of ICD-11 concepts (`concept_synonyms`, migration `0014`) from the files it already reads, in the transaction that replaces each ontology: the MONDO import its labels and EXACT synonyms, the ICD-10-CM import its index's main terms (`icd10cm-index-<year>.xml` in the pinned archive). No new download. Its report line names the count (pinned releases: 11,174 from MONDO and 3,231 from the ICD-10-CM index, 14,405 in all over 2,976 ICD-11 concepts, 663 of them depth-1 conditions; about 0.6 s more for both).
- **`/meta` `ontologies`** (always sent): ICD-11 first (`is_default` true, its release, licence, attribution, and sizes; `mapping_counts` null), then each imported ontology in toolbar order with its release, licence, attribution, sources, sizes (`counts`: chapters, blocks, depth-1 conditions, level-2 concepts), and `mapping_counts` (depth-1 conditions by kind). A store without an import lists ICD-11 alone.

### 23.1 Shapes

- **ICD-10-CM** (D2): the disease chapters only, 1–17 and 19 (the ICD-11 atlas also leaves out symptoms, external causes, factors, and codes for special purposes); chapter ids `CM-CH-<nn>` with `chapter_no` the chapter number; sections as blocks (`CM-BLK-<range>`, `code` the range, e.g. `E08-E13`); three-character categories as conditions (depth 1, the code is the concept id); their four-character subcategories at depth 2 with the category as `metric_anchor_id`. Codes of five or more characters are left out. Pinned release: 18 chapters, 233 blocks, 1,467 conditions, 9,295 level-2 concepts.
- **MONDO** (D4, R0): the live terms under "human disease" (MONDO:0700096). Chapters are a hand-written list in ring order, which is also the priority order (`app/ontologies/mondo.py` `CHAPTERS`): cancer or benign tumor, disease of primarily extrinsic mechanism (infections and injuries), psychiatric disorder, sleep disorder, obstetric disorder, metabolic disease, the subclasses of "disease by body system or component" in an ICD-like order, then syndromic disease and, last, the two remaining groupings of human disease (disease by developmental or physiological process; disease by etiologic mechanism), which collect the terms no other chapter holds. Each term's chapter is the first chapter that contains it. Blocks are the chapter's direct subclasses; **a direct subclass without subclasses of its own in the chapter is gathered with the chapter's other leaves in one block "Other <chapter>"** (id `<chapter id>-other`, no code), so that a chapter never shows hundreds of one-condition blocks (syndromic disease would have had 634 blocks, 582 of them single leaves). Every other term sits under its primary parent, the first of its parents inside the chapter by label: depth 1 under a block, deeper terms at `depth_in_kind` 2 or 3 (anything deeper counts as 3) with the block as `parent_id` and their depth-1 ancestor as `metric_anchor_id`, as in the ICD-11 atlas. Other parents are kept for the condition card. MONDO has no chapter numbers: `chapter_no` is the chapter's ring position. Labels are shown with a capital first letter. Pinned release: 27 chapters, 285 blocks (22 of them "Other" blocks), 3,039 conditions, 22,970 level-2 concepts; of the 23,262 human-disease terms, 27 are chapters, 263 blocks, and 2 grouping terms ("disease by body system or component", "acute disease") are in no chapter.
- **Concept records** of another ontology have `icd11_code` null and the ontology's own `code` (additive field, absent on ICD-11 records). Conditions carry no `fsn` (MONDO's largest chapter stays within the 2 MB budget, §10).

### 23.2 Crosswalk

Every level-2 concept has one mapping with a **kind**:

- **Resolving an ICD-11 MMS code** to the atlas: the level-2 concept with that code (`exact`); else the code with its last character after the dot dropped, repeatedly (5A13.12 → 5A13.1 → 5A13), until a level-2 concept has it (`stem`); else the atlas block whose block id ends in the code's first three characters (`block`, e.g. 5A0Q → BlockL1-5A0); else nothing.
- **ICD-10-CM** (and MONDO's ICD-10 references): the longest prefix of the code, at least a three-character category, that WHO's `10To11MapToOneCategory` table maps (category rows only: chapter rows carry Roman numerals such as "I" that would otherwise match), then its ICD-11 code resolved as above. No such prefix, or a code that does not resolve: `none`.
- **MONDO:** the first cross-reference that resolves, in this order: every `icd11.foundation` reference (the Foundation entity's MMS code from WHO's `foundation_11To10MapToOneCategory` table, else the `ICD-11 FoundationURI` column of `10To11MapToOneCategory`), every `ICD10CM` reference, every `ICD10WHO` reference. Otherwise the term inherits the mapping of its **nearest directly mapped parent at most two `is_a` steps up** (`parent`, with `via` and `steps`; among parents at the same distance the first by label; only parents the import holds count). Otherwise `none`. Inheriting from any ancestor would reach far more terms through very broad parents, so it is not done (R0).
- **Stored per concept:** `kind`, the ICD-11 `target_concept_id` (a level-2 concept for `exact` and `stem`, a block for `block`, and for `parent` whatever the via concept's own mapping names), `via_concept_id` and `steps` (`parent`), the `source` (`who-icd10-icd11`, `mondo-icd11-foundation`, `mondo-icd10cm`, `mondo-icd10who`), the `source_code` it was read under (the WHO ICD-10 code, the foundation id), and the ICD-11 MMS `icd11_code` the source named.
- **Coverage of the pinned releases** (depth-1 conditions; the import prints it, `/meta` serves it): ICD-10-CM 984 exact (67 %), 9 stem (1 %), 155 block (11 %), 319 none (22 %: 267 whose ICD-11 target the simplified atlas lacks, 52 without a WHO ICD-10 code), exactly the R0 numbers. MONDO 407 exact, 5 stem, 20 block, 1,311 parent, 1,296 none (43 %); over all 22,970 level-2 concepts 2,922 exact, 26 stem, 85 block, 11,095 parent, 8,842 none (61.5 % mapped; R0 measured 52 % over all human-disease terms with only the 10 → 11 table's foundation column, 8,224 foundation ids; the foundation table adds the rest).

### 23.3 Projection (the reads)

`ontology=<id>` (pattern `^[a-z0-9][a-z0-9-]{0,31}$`; `icd11` is the same as leaving it out) is accepted by `getAtlasOverview`, `getChapter`, `getMetricMap`, `getMetricSummary`, `getConceptMetrics`, `getConceptSubgroups` (§24), `searchConcepts`, and `exportConcept`. An id the store has not imported returns 404 `unknown_ontology`; a malformed one 422 `invalid_parameter`; a concept or chapter id of another ontology (or of ICD-11 in an ontology read) 404 `unknown_concept`. It combines with `version` (§2) and `population` (§21). The catalogue, the multimorbidity reads, `exportDataset`, and `lookup` stay ICD-11.

- **Conditions.** `exact` and `stem` serve the row of their ICD-11 concept (a deeper ICD-11 category serves its anchor's row, §5) with their own `concept_id`; `block` serves the ICD-11 block's rollup (§6, with its `provenance.rollup` and, in the map, its `child_count`); `parent` serves what its via concept's mapping names; `none` serves no row (`metrics` null; every map status `no_data`) and is presented as **No mapping** (§13). Grades, statuses, warnings, safeguards, and provenance are the ICD-11 row's, so the evidence derivation and its prevalence penalty are those of the mapped ICD-11 concept. `provenance.data_source` (§11.3) is the ICD-11 row's.
- **Blocks and chapters** of another ontology are rollups (§6 rules) over the **distinct** depth-1 ICD-11 conditions (anchors) that their level-2 concepts (deeper ones included) reach, in the order first reached: an `exact`, `stem`, or `parent` concept reaches its target's anchor, a `block` concept every condition of the ICD-11 block, `none` nothing. Each anchor counts once, however many concepts reach it; weights are the anchors' ICD-11 prevalence scores; the rollup's chapter for the evidence derivation (§4.2) is the anchors' ICD-11 chapter when they share one, else none. `child_count` is the number of anchors with a row at the lens.
- **Prevalence** (bubble sizes and display prevalence, §5, §13): a level-2 concept takes the tier and score of its ICD-11 target concept (`exact`, `stem`, and `parent` to a condition), the median tier of the ICD-11 block's conditions (`block`, and `parent` to a block), or the neutral tier **uncommon** (`none`). A local population's tiers reach the projection through these ICD-11 concepts.
- **Safety** (§18): a concept shows the marks and incidents of its anchors: an incident keyed by ICD-11 codes or a chapter appears on every concept mapped to those conditions; a rollup takes the worst mark of its anchors. Incidents never change results.
- **Responses** name the ontology (`ontology: {id, name}` after `population`, header `X-Ontology`); ETags and the response cache are keyed by it. `getMetricMap` adds `mapping`, an array aligned with `rows`: each condition's kind, null for block and chapter rows, and `none` for a block or chapter none of whose conditions maps (no anchor at all; it is presented as No mapping, not as a rollup without children) (the `columns` list is unchanged). `getMetricSummary` adds `mapping_counts` over its depth-1 conditions (`none` ones count as `no_data`). `getConceptMetrics` adds `mapping` (a `ConceptMapping`: kind, the ICD-11 concept as `icd11` {concept_id, code, pt, level}, `via` {concept_id, pt}, `steps`, `source`, `source_code`, `icd11_code`; null for blocks and chapters, kind `none` for one none of whose conditions maps) and, for a condition, `other_parents` (the parents besides the primary one; empty for ICD-10-CM). `exportConcept` names the ontology and puts the ontology's own `code` and the `mapping` in `concept`.
- **Search** (§9) runs over the ontology's concepts with its own codes.
- **ICD-11 is unchanged.** Every read without `ontology`, or with `ontology=icd11`, is byte for byte what it was before v1.13 (`tests/test_ontologies.py::test_icd11_reads_are_byte_identical` compares a fixed set of reads on stores with and without imported ontologies); only `/meta` gains `ontologies`.
- **Multimorbidity** stays ICD-11: combinations are stored and selected by ICD-11 anchors (§8), so in another ontology the frontend disables the Multimorbidity mode and says why.
- **Budgets** (§10): the same as for ICD-11. A projection is built on the first read of an ontology for a version and population (about 0.5 s for MONDO, 0.2 s for ICD-10-CM) and kept with the version's context; later reads cost what ICD-11 reads cost.

## 24. Subgroups (v1.13)

Added 2026-10-20 (release 0.4). The condition card's **Across groups** section compares one concept's result at all patients with its result at every one-group lens, in one request, and marks groups that differ. All data is synthetic. **The difference flag is a prototype heuristic, not a grade: it changes no grade, status, score, warning, safeguard, or mark.**

- **Read.** `getConceptSubgroups` (`GET /metrics/concepts/{concept_id}/subgroups`, tag `metrics`) takes `model`, `use_case`, `version` (live or staged, §2), `population` (§21), and `ontology` (§23), and no lens parameters: one response holds every lens. Validation, lookups, and errors are those of `getConceptMetrics` (§3: 422 before 404; `unknown_model`, `unknown_use_case`, `unknown_concept`, `unknown_population`, `unknown_upload`, `upload_not_valid`). It carries `X-Dataset-Version`, an `ETag` (304 on `If-None-Match`), and, for a local population, `population` and `X-Population`; its server cache and ETag are keyed by concept, card, version, and population like every read.
- **One-group lenses.** Every specific value of each axis with the other two axes at `All …`, in axis order (age, sex, ethnicity) and value order of `/meta.axes`: 4 age, 2 sex, and 5 ethnicity groups in the seed, 11 in all. Combined lenses (two or three groups at once) are not listed.
- **Entries.** `all_patients` (axis `all`, `group` null) and `groups` (axis and the lens value, e.g. `Age 65+`) are each a `SubgroupResult`: the `lens`, `has_result`, and from the row `getConceptMetrics` serves for the concept at that lens (§4–§7: stored, deeper category through its anchor, rollup, or lens fallback, study adjustments included) its `perf`, `ci_low`, `ci_high`, `performance_grade`, `evidence_grade`, `overall` (tier, score, grade), `status` (overall, performance, evidence; §4.5), `intended_use_level`, `provenance` (with `lens_fallback` and, for a stored row at the lens, `data_source`, §11.3), and since v1.14 `n_samples` and `n_sites` (the group's patients or cases and sites; for a rollup or a lens fallback the mean of its rows, as `getConceptMetrics` serves it; null without a row or a count), plus the concept's `safety` mark at the lens (§18). Without a row the entry has `has_result` false, null values, statuses `no_data`, the tier `no_data`, and `provenance` null. A rollup without children at a group (§6, e.g. a product that stores only the all-patients lens) has a row whose `provenance.rollup.child_count` is 0 and no `perf`; clients present it as No data (§13, V1). A card that stores only all-patients rows (a product) therefore has no result at any group and no flag.
- **Difference** (groups only; absent on `all_patients`): `delta` = group `perf` − all-patients `perf`, rounded to 3 decimals (null when either is null); `direction` `higher` or `lower` (null when `delta` is 0 or null); `flagged`; and `reason`:
  - `no_result`: either `perf` is null (not flagged);
  - `below_delta`: `|delta|` < `min_delta` (not flagged; compared with a 1e-9 tolerance, so a difference of exactly 0.05 counts);
  - `missing_ci`: a confidence bound is null on either side (not flagged, however large `delta` is);
  - `ci_overlap`: the intervals `[ci_low, ci_high]` overlap; touching bounds count as overlapping (not flagged);
  - `separated`: `|delta|` ≥ `min_delta` and the intervals do not overlap (**flagged**);
  - `layer_differs`: a local group without a local all-patients result to compare with (not flagged; below).
- **Layers** (added 2026-10-20, additive). With a local population (§21) whose local results the card has (§26), a group is compared only with an all-patients result of the **same evidence layer**; otherwise the read is unchanged, byte for byte (test). Then every entry carries `layer`: `local` (a local result), `includes_local` (a block or chapter with at least one local condition, §26.1), `public`, or null without a row; when `all_patients` is not `public`, the body adds `public_all_patients`, the card's public all-patients result under the same prevalence (an entry with `layer` `public`, or without a result). Each group's `difference` adds `compared_with`, the layer it was compared with: a group of the same layer as `all_patients` is compared with it; a `public` group otherwise with `public_all_patients` (`compared_with` `public`); a `local` or `includes_local` group whose all-patients result is of another layer is not compared: reason `layer_differs` (not flagged, `delta` null, `compared_with` null). A group without a row has `compared_with` null and reason `no_result`. Clients say on each row whether it is a local or a public result and which all-patients result it was compared with. In another ontology (§23) the layers come from the ICD-11 rows the concept reaches.
- **Published rule.** `/meta.subgroup_difference` = `{min_delta: 0.05, requires_ci_separation: true, note}`; the note says that it is a prototype heuristic and not a grade. Clients word the flag from it; they never restate the numbers.
- **Fallback and sources.** A group served by lens fallback (§7: the set does not define that lens, so its rows are aggregated over the matching narrower groups) has `provenance.lens_fallback` true; clients say "worked out from related groups". `data_source` is that of `getConceptMetrics` (null for aggregated rows).
- **Budget.** About 8 KB; under 20 KB; p95 within 150 ms uncached on the seed store, chapters included (§10).
- **Group summary (v1.14).** `getSubgroupSummary` (`GET /metrics/subgroups/summary`, tag `metrics`) takes `model`, `use_case`, `version`, `population`, and `ontology`, validated like every read (422 before 404; `unknown_model`, `unknown_use_case`, `unknown_population`, `unknown_ontology`, `unknown_upload`, `upload_not_valid`). It always counts the card's **depth-1 ICD-11 conditions** (`classification_basis: "icd11"`, `total`), whatever ontology is named: another classification's conditions reach the same ICD-11 rows, and counting them would count rows twice. So the answer names no ontology and carries no `X-Ontology`; it is identical for every `ontology`. `all_patients_with_result` counts the conditions with a performance value at all patients. For each one-group lens (`groups`, in the order of `getConceptSubgroups`):
  - `with_result`: conditions with a performance value in the group; `no_result`: conditions with one at all patients but none in the group (a group with `with_result` 0 has **no data**);
  - `compared`: conditions whose group value was compared with an all-patients value (a `delta` exists); `flagged_higher`, `flagged_lower`: those the difference rule above flags (`separated`), by direction;
  - `flagged`: up to **5** flagged conditions (`concept_id`, ICD-11 `code`, `pt`, `chapter_id`, `delta`, `direction`), largest `|delta|` first, then in ICD-11 order.

  The rule and the layers are exactly those of `getConceptSubgroups`: with local results for the chosen population (`layered` true) a group is compared within its layer, a public group with the public all-patients result. A condition's counts equal what `getConceptSubgroups` says for it (`tests/test_subgroup_summary.py`). It carries `X-Dataset-Version`, an `ETag` (304 on `If-None-Match`), and for a local population `population` and `X-Population`; its cache and ETag are keyed by card, version, and population. Budget in §10. **It is a heuristic, never a grade**: it changes no status, and clients word it as "differs from all patients", never as bias detected. The Summary shows it as "Across groups": the groups with the most flagged conditions (higher and lower), the groups without data, and links that open a listed condition (ICD-11 only).
- **Static demo.** Recorded for ICD-11 conditions (depth 1) only: the static adapter answers those from the recorded bundles and rejects chapters, blocks, deeper categories, and other classifications with `static_unavailable`, and the condition card says so in words. Since release 0.5 Across groups is also recorded at each care setting a card stores (§29: the groups within it), and `getSubgroupSummary` (v1.14) per card at Any setting and at each stored setting: the answer counts ICD-11 conditions whatever the classification, so one recorded file serves every `ontology`; a local population is `static_unavailable` (in words), as everywhere.
- **Ontologies (§23).** The optional `ontology` parameter is validated, keyed, and named as for `getConceptMetrics` (422 for a malformed id, 404 `unknown_ontology`; `X-Ontology` and `ontology: {id, name}`; ETag and response cache keyed by it; `icd11` or none is byte for byte the ICD-11 answer). The concept resolves through the projection: each entry is the projected row at its lens (a mapped condition serves its ICD-11 row, a block or chapter the §23 rollup), with `data_source` of the ICD-11 row, and the body adds `mapping` (the `ConceptMapping` `getConceptMetrics` serves; null for chapters and blocks). An unmapped concept (kind `none`) answers with its mapping and no result at any lens, so nothing is flagged.
- **Frontend.** The condition card's "Across groups" section is about population groups and is kept apart, in words and look, from "Study quality" (§22), which is about the underlying study. Choosing a group switches the atlas to that one-group lens.

## 25. Comparison (v1.13)

Added 2026-10-20 (release 0.4). `getComparison` (`GET /compare`, tag `compare`) puts **2 to 4 cards** side by side over the same rows and says, per row, whether their results can be read against each other at face value. The backend owns the rule; clients own the words. The rule is a deterministic **prototype heuristic**, published in `/meta.comparison` (`heuristic: true`); it never changes a grade, a status, or a score. All data is synthetic demonstration data.

- **Request.** `cards` is a comma-separated list of 2 to 4 distinct card ids `<model_version>|<use_case>` (URL-encoded; `|` separates the two, so a use case must not contain one). Fewer than 2, more than 4, a repeated card, or an id without both parts is 422 `invalid_cards`; parameter validation (422) precedes lookups (§3), and an unknown model or use case is 404 `unknown_model` / `unknown_use_case`. `scope` is `atlas` (default) or `chapter`, which needs `chapter_id` (422 `missing_chapter_id`; a concept that is not a chapter of the chosen ontology is 404 `unknown_concept`). The lens (§3) with its care setting (`context`, §29), `version` (§2), `population` (§21), and `ontology` (§23) work as on `getMetricMap`; the setting applies to every column. The card order of the request is the column order of the answer.
- **Rows.** At `atlas` scope one row per chapter of the chosen ontology, in chapter order. At `chapter` scope the chapter's blocks in order, each followed by its depth-1 conditions (deeper categories are left out; they serve their anchor's row, §5). A row carries the concept (`concept_id`, `code` in the chosen ontology, `pt`, `level`, `parent_id`, `chapter_no`), its crosswalk kind in another ontology (`mapping`, §23; null for ICD-11 and for rollups, `none` for a rollup none of whose conditions maps), one **cell** per card, `comparable`, `reasons`, and `perf_spread`. `filters` echoes the context, the lens, the scope, `chapter_id`, and `chapter_pt` (the chapter's preferred term, null at atlas scope).
- **Cells.** Each cell is what `getMetricMap` serves for that card, concept, and lens: `status` (the Overview status), `performance_status`, `evidence_status`, `perf`, `ci_low`, `ci_high`, `evidence_grade`, `validation_type`, `lens_fallback` (`provenance.lens_fallback`, §7), and `safety` (the open-incident mark, §18), plus `study_design` (the design of the study a stored row links, §22, else null) and `design_group` (below). `status` is the status **as clients present it**: a rollup without children (§6) and a concept without an ICD-11 mapping read `no_data`, and a `no_data` cell carries no values (every value null, `lens_fallback` false; `safety` is kept).
  - *v1.14 (release 0.5):* a cell with values (not `no_data`) adds `layer`, the §26.1 layer of its result (`local` for a condition served from local results, `includes_local` for a block or chapter with at least one, else `public`, as the map's `layer` says), **only when the card has local results for the requested population** (in every ontology); and `setting_category`, the setting category (§22) of the study its stored row links, **only when that study states one**. Both are left out otherwise, never sent as null, so every cell of a read without local results or setting categories is what v1.13 served.
- **A result.** A card has a result on a row when its cell's status is `strong`, `moderate`, or `weak`. `out_of_scope` and `no_data` are not results. `perf_spread` is the largest difference in `perf` between the cards with a result (3 decimals), null when fewer than two have one; clients sort by it ("largest difference").
- **Design groups** (`/meta.comparison.design_groups`): the kind of evidence behind a result. `clinical_study`: validation types `clinical_study_multisite` and `clinical_study_single_site`, study designs `retrospective`, `prospective`, `real_world_deployment`, `randomized_trial` (the system measured in care or on care records). `test_cases`: `benchmark`, `vignette_study`, `simulation_study`, and the designs `benchmark`, `vignette`, `simulation` (cases built or chosen for testing). `internal_test`: `internal_test` (the developer's own test data). A cell's group is its linked study's design group when the stored row links a study, else its validation type's group; a cell without either has none.
- **Card facts** (`cards`, one per card, in request order): `card_id`, `model_version`, `use_case`, `display_name`, `kind`, `developer`, `status`, `function_category`, `intended_use_defined` (§11.1); `lenses` (`stored`: how many lens combinations the card stores at the requested setting; `total`: 90; `all_patients_only`: it stores the all-population lens only at that setting, as the demo's three pack-v1 products do at Any setting; `requested`: whether the requested lens is `stored`, can be combined from narrower groups by §7 (`fallback`), or has `none`; since v1.14 `settings`, the care settings it stores rows for, sent only when one is specific, §29); `studies`, the study records (§22) linked to any stored row of the card at any lens of the requested setting (a set's default source counts at every setting the card stores), in stored order; `validation_types`, those of the card's depth-1 ICD-11 conditions at the requested lens, in §4.2 order; and `design_groups`, the groups of those types and studies. Card facts do not depend on the ontology.
  - *v1.14 (Q4):* after `design_groups`, `performance_measure` and `reference_standard` (§28.1), each only when the card states it; `configuration` `{configuration_id, configuration_date}` (§28.1, each null when not given), only when the card states one of them; `narrow_model_card` `{present, submitted_at}`: whether the card's AI system has a narrow model card (§26.4) in the version read, and when it was submitted (null without one); and `conductors` `{developer, independent, hospital}`: the card's linked `studies` counted by who conducted them. The last two are always sent; they describe the narrow model card and the evidence's conductor mix beside the results, never as a grade or a ranking.
- **Reasons.** `reasons` lists `{code, cards}` in this order; `cards` are the card ids the reason concerns, in request order. A row is `comparable` exactly when every card has a result and `reasons` is empty.
  - Card level, on every row (also in `card_reasons`):
    1. `function_category_differs`: the cards state at least two different function categories (§11.1). Concerns the cards outside the most common category (the first card's on a tie). Different categories mean different tasks (for example triage against decision support), so the figures measure different things.
    2. `function_category_unknown`: a card states no function category, so whether the tasks match is unknown. Concerns those cards.
    3. `population_differs`: the lens is not the all-population lens at Any setting, and some cards have `requested` `none` while at least one other card has data for the group. Concerns the cards without data. They hold a different evaluation population (for example a product that stores all patients only). Since v1.14 (§29) the requested lens includes the care setting, so a card that stores no rows at a requested specific setting (while another card does) is flagged the same way; the facts' `lenses.settings` tell the two cases apart, and the frontend words it "no data for this group or setting". No separate reason was added; `setting_differs` (Q4) compares the studies' setting categories instead.
    4. `measure_differs` (v1.14): the cards state at least two different performance measures (§28.1; compared ignoring case and spacing). Concerns the cards that state a measure outside the most common one (the first card's on a tie). The figures then measure different things (for example top-3 diagnostic accuracy against sensitivity).
    5. `measure_unknown` (v1.14): some cards state no performance measure while at least one other card states one, so whether the figures measure the same thing is unknown. Concerns the cards without one. **When no card states a measure, neither measure reason is added**: the cards predate the field, and such a comparison reads exactly as under v1.13.
  - Row level:
    6. `no_mapping`: in another ontology, the concept has no ICD-11 mapping (`mapping` `none`): no card can show a result. Concerns every card; no other row-level reason is added.
    7. `mapped_broader`: in another ontology, a condition (level 2) mapped `block` or `parent`: every card's result describes an ICD-11 subchapter or a broader parent, not the concept itself. Concerns every card.
    8. `no_result`: a card's status is `no_data`. Concerns those cards (all of them when none has a result).
    9. `out_of_scope`: a card's status is `out_of_scope` (its intended-use statement excludes the row). Concerns those cards.
    10. `lens_fallback`: among the cards with a result, some results were combined from narrower groups (§7) and others were stored for the group. Concerns the cards that fell back. When every card fell back, they describe the group the same way and nothing is flagged.
    11. `design_differs`: the cards with a result and a design group span at least two groups. Concerns the cards outside the most common group (the first card's on a tie).
    12. `setting_differs` (v1.14): among the cards with a result, the cells' `setting_category` values (the linked studies' setting categories) span at least two categories. `mixed` names no single setting and does not count, nor does a cell without one (no linked study, or one that states none). Concerns the cards outside the most common category (the first card's on a tie). Rollups link no study, so only conditions can carry it.
- Free-text settings, conductors, and populations of the linked studies are context: they are shown in the card facts, not compared by the rule (v1.14 compares the setting *category* only, reason 12).
- **Responses** name the population and the ontology as the atlas reads do (§2): `population` and `X-Population`, `ontology` and `X-Ontology`; ETags and the response cache are keyed by the cards in order, the lens, the scope, the chapter, the version, the population, and the ontology. `ontology=icd11` is the same as none.
- **Budgets** (§10): four cards, warm, under 300 ms at both scopes and under 2 MB (`tests/test_comparison.py`).
- **Static demo.** The static build records each card's facts and cells per lens and classification and applies a port of this rule (`frontend/src/api/staticComparison.js`), which the recorder checks against the API at every recording. The v1.14 rule changes are in the port too, and `backend/tests/fixtures/comparison_rule_cases.json` holds shared cases that both `tests/test_comparison_q4.py` (the backend rule) and `tests/compareDepth.test.js` (the port) must answer alike. Recorded cells keep `layer` and `setting_category` in their arrays (null when absent) and leave them out again when decoding, as the API does.
- **Frontend.** The comparison page (`frontend/compare.html`) names the lens, population, and classification next to the results (D10), shows the card facts side by side, and the rows with each card's mark, value, CI, and grade; a row that is not comparable says **Not directly comparable** with the reasons in words. It never ranks the cards or names a winner. Since v1.14 the facts include what each card's figures measure and against what, its configuration, its narrow model card, and who conducted its linked studies; the reasons name the measures ("Measures differ: top-3 diagnostic accuracy vs sensitivity") and settings; and a cell from a local result carries a **Local** tag beside its value.

## 26. Local results, instance, roles, and nested model cards (v1.13)

Added 2026-10-20 (release 0.4; E7–E9). All data is synthetic demonstration data. There is **no authentication**: roles are workspaces a user chooses, and publishes record that choice with an entered name.

### 26.1 Local evaluation results

- **Data set.** Kind `local_metrics`: one content set per card (`model_version`, `use_case`) and local population (`population_id`, §21), stored like a metrics set (migration `0010`). Its template is the metrics template (§11), the population chosen at upload (`createUpload` form field `population_id`; the records upload's `population_id`). Replace and merge uploads (§11.2), the records upload, staged reads, the change summary, History, and restore work as for metrics; one staged upload per card and population. A replace upload needs no common lens coverage (local rows replace public rows one by one). Removing a population (§21) removes its local results too; a restore brings both back.
- **Validation.** The population must be published (`unknown_population`, a whole-file error). Every row that adds or replaces a result names, in its Study column, a study of the version's studies set with `scope` `hospital` and `population_id` equal to the upload's population: no Study is `local_study_missing`, any other study (unknown, public, or another population's) is `local_study_mismatch`, each with a plain fix. Staged local results are checked again after a studies, population, or registry publish or a rollback. Performance needs evidence (§11) as everywhere.
- **Studies and incidents.** `Study` gains `scope` (`public`, the default, or `hospital`) and `population_id` (required for `hospital`, a published local population, `unknown_population` otherwise; empty for `public`, `population_without_hospital_scope` otherwise); a staged studies upload is checked again after a population publish or removal; `SafetyIncident` gains `scope` (`public` or `hospital`, an incident a hospital recorded itself). Template columns Scope and Local population are optional; files without them stay valid and public. Both fields are always served.
- **Overlay (D8).** A read with `population=<id>` (§21) of a card that has local results for that population serves, for each condition and lens, the **local row when the local set stores exactly that condition and lens**, else the public row as before (including the public demographic fallback, §7; local rows are never combined by the fallback). A deeper category serves its anchor's row (§5). Every derivation uses the overlaid rows: rollups (§6), the Overview and summary (§4.5, §14), the catalogue's tiles for that population (§17), the comparison (§25), lookup (§19), and exports (§14). Local rows are graded like any stored row (§4.2), with their study link (§22). Grading formulas are unchanged.
- **Marked.** A served local row has `provenance.layer` `local` (absent on public rows, which keep their exact shape); its `data_source` is the local row's source. `getConceptMetrics` adds `public_metrics` beside a local row: the card's public row for the same concept and lens under the same prevalence (with its own `data_source` and `appraisal`), or null when there is none; the field is absent otherwise. `getMetricMap` (ICD-11 reads) adds `layer`, an array aligned with `rows`: `local` for a condition served from local results, `includes_local` for a block or chapter with at least one such condition, else null; it is present only when the card has local results for the population. Reads in another ontology (§23) serve the overlaid ICD-11 rows and carry `provenance.layer` and `public_metrics` (the mapped public row) in concept reads, but no `layer` array.
- **Unchanged answers.** A read without `population`, or for a population without local results for the card, is byte for byte what it was before local results were published (test).
- **Care settings (v1.14, §29).** A local row is stored for one setting like a public row (the Setting column); with the population chosen it replaces the public row of exactly its condition, lens, and setting.
- **Change summary.** Rows compare the staged local set with the live one of the same card and population. Status shifts compare the card's all-population answers for readers of the population before and after (live versus staged local set). The version summary reads "Local results for <card>, local population <id>: …, N overall status changes for readers of the local population." Kind `local_metrics` versions never move a tile's `last_updated` (§17).

### 26.2 Instance profile

- `/meta.instance` (`InstanceProfile`, always sent): `kind` (`public` or `hospital`), `organisation`, `maintained_by` (each 1–120 characters), optional `contact` (≤ 200), and (v1.14) the optional `data_protection_note` (≤ 500): the organisation's own note on how patient data is handled where the tool is used (a hospital's note, for example). It is sent only when set, so a profile without it reads as before. A fresh or migrated store reads `public`, "Broad Modelcard (demonstration)", maintained by "the Broad Modelcard project".
- `updateInstance` (`PUT /admin/instance`) sets it (422 for other kinds or empty names, or a note over 500 characters). It sets the whole profile: a `contact` or `data_protection_note` left out (or null) is cleared. Whitespace runs are collapsed. It is not a dataset version: it names who runs this copy of the tool, not the data; the response cache is cleared so `/meta` serves it at once.

### 26.3 Roles and submissions

- **Roles.** `publishUpload`, `rollbackVersion`, `removePopulation`, `acceptSubmission`, and `publishReleaseImport` take an optional `role` (`custodian`, `hospital`, `maintainer`; `developer` is refused with 422, since developers submit) and `publisher_name` (≤ 80). The version stores both (`publisher_role`, `publisher_name`; null for older versions and when not given) and History serves them. They are a recorded choice, not an authenticated identity.
- **Submissions.** `createSubmission` opens a developer submission (`submission_id`, `developer_name`, `model_version`, `created_at`, `status` `submitted`, optional `note`). Uploads join it with `submission_id` (`createUpload`, `createRecordsUpload`, `createModelCardUpload`); a submission may stage an AI system's registry rows as records (kind `models`, a merge of that entry into the live registry) and holds at most one staged upload per data set (and card), apart from the data sets' own staged uploads, which are unaffected and do not list them (`listDatasets`). A submission's parts are checked against each other: a new card's metrics count as present for its registry rows, and the parts are checked again when another part joins. **Nothing in a submission publishes on its own**: `publishUpload` answers 409 `submission_upload`.
- **Custodian review.** `listSubmissions` (newest first, optional `status`) and `getSubmission` serve each submission with its uploads; their change summaries and staged reads (§2) work as for any upload. `acceptSubmission` (optional `note`, `publisher_name`) requires every staged part to be valid (409 `submission_not_ready`) and publishes them one version each, with the note, role `custodian`, and the name, in the order the store's rules need: metrics (a new card's metrics before its registry row, §11), multimorbidity, the registry entry, studies, the narrow model card, then the rest; the submission becomes `accepted` with `published_versions`, `decided_by`, `decided_at`. Should a part fail its renewed check midway, the versions already published stay, the submission stays `submitted`, and the 409 names the part. `returnSubmission` requires a note, discards the staged parts (nothing was published), and marks it `returned`; the developer submits again. A decided submission takes no new parts and no second decision (409 `submission_closed`). One decision runs at a time: an accept or return sent while an accept is publishing answers 409 `publish_in_progress`.
- **Evaluation results in a submission (v1.14, §32.2).** A developer may add evaluation results files (`createEvaluationUpload` with `submission_id`; the Data Library's Submit an AI system offers one). Such a part is checked with the others and must be valid before an accept, like every part, but it publishes nothing itself: the custodian stages its proposed study and metrics records into the same submission (records uploads with `submission_id`), and accepting publishes those parts in the usual order; the evaluation part then reads `published` (without a version). A submission whose staged parts are evaluation results only answers 409 `submission_not_ready` ("stage their proposed records first"). Returning a submission discards its evaluation parts like every part. Since a submission holds one staged upload per data set and card, proposed records cannot join a submission that already has a studies part, or a metrics part for the same card (409 `staged_upload_exists`); the custodian then returns it, or merges the records in the Data Library after accepting.

### 26.4 Narrow model cards

- **Data set.** Kind `model_cards`: one global content set, at most one card per AI system (`model_cards`, migration `0010`), versioned like every kind. `createModelCardUpload` (`POST /admin/uploads/model-card`, JSON `{model_version, format, content, filename?, submission_id?, replace_staged?}`, at most 1 MB) stages one AI system's card as a merge into the live set, checked in the background; one staged card per AI system (and submission). There is no spreadsheet template (`downloadTemplate` answers 422).
- **Formats.** `json`: the prototype's schema, mirroring the Hugging Face model-card metadata: `name` (required), `version`, `license` (or `licence`), `intended_use`, `limitations`, `training_data`, `date`, and results as a Hugging Face `model-index` (`[{name, results: [{task, dataset, metrics: [{type, value, name}]}]}]`) or a flat `results` list (`[{task, dataset, metric, value}]`); any result may name `icd11_codes`, `use_case`, `samples`, `sites`. `markdown`: kept as text; an optional `---` front matter is read with a small hand-written parser that accepts only flat `key: value` lines and simple `- item` lists (no YAML library); every other construct (nested maps such as `model-index`, flow collections, block scalars, anchors) is the note `unsupported_front_matter` with its line ("convert this part to JSON") and is skipped. `## Intended use`, `## Limitations`, and `## Training data` sections fill those fields. Errors: `invalid_model_card` (unreadable JSON, unterminated front matter), `model_card_field` (a wrong field), `unknown_target` (an AI system in neither the live nor a staged registry).
- **Read.** `getNarrowModelCard` (`GET /models/{model_version}/narrow-model-card`, a read with `version`, ETag, and 304) serves `{dataset_version, model_version, narrow_model_card}`: the parsed card, its `source_format`, the Markdown text, and `submitted_at`, or null when the AI system has none; 404 `unknown_model` for an AI system the version lacks. The card is the developer's own and never verified.
- **Proposed records.** `getModelCardProposals` (`GET /admin/uploads/{upload_id}/proposed-records`, a valid narrow model card upload only, 409 otherwise) proposes, for each result with ICD-11 codes and a value between 0 and 1, a metrics record per code (its top-level condition; a subcategory proposes its anchor) at the all-population lens: the value as Performance, Validation type Benchmark, `samples` and `sites` when given, the stored row's intended-use fields and warnings (a merge row replaces the whole row, §11.2), and Source "Narrow model card: <name> <version>", Study the dataset, Source date the card's date. Batches are per card (the result's function, else the AI system's default function); skipped results name `unknown_code`, `no_function`, or `value_out_of_range`. **Nothing is staged**: the custodian or a maintainer sends a batch to `createRecordsUpload` (in the same submission when there is one), which stages a merge that is checked, reviewed, and published like any other.

### 26.5 Public release bundles

- **Export.** `exportPublicRelease` (`GET /admin/release/export`, public instances only, 409 `not_public_instance` otherwise) streams a gzip-compressed SQLite file of the live **public layers**: the registry, every card's metrics and multimorbidity, the default prevalence, the public safety incidents, the public studies, the effects on outcomes (§27), and the narrow model cards, with the interned warning lists and row sources they use, and a manifest (`bundle_manifest`): format and format version, the dataset version, time, organisation, an atlas fingerprint (concepts and lens axes), the sets, and per table its row count and SHA-256. Local populations, local results, hospital studies, and hospital incidents are never exported.
- **Import.** `importPublicRelease` (`POST /admin/release/imports`, multipart `file`, hospital instances only, 409 `not_hospital_instance` otherwise) accepts bundles up to **512 MB** (expanding to at most 2 GB, at most 100:1), apart from the 128 MB limit of data set uploads. It checks the format and the manifest's shape (its tables are exactly the bundle tables, its sets name only public kinds and match the bundle's sets), that every table has the store's columns (a bundle of another schema version is `invalid_bundle`), every table's count and checksum (`bundle_checksum`), and the atlas fingerprint (`bundle_atlas_mismatch`); a bundle that cannot be read is an `invalid` import with `invalid_bundle`, never a server error. It serves a `ReleaseImport`: `status` `valid` or `invalid` with `problems`, the release, `changes` per public data set (`added`, `changed`, `removed`, `unchanged`: AI systems, cards' metrics, multimorbidity, prevalence codes, public studies, public incidents, narrow model cards), what stays (`keeps`: local populations, local results, hospital studies, hospital incidents), and notes (a hospital record whose id the release also uses keeps the hospital record; local results of cards the release no longer lists stay, unread). Nothing is published yet; `getReleaseImport` reads it again and `discardReleaseImport` drops it.
- **Publish.** `publishReleaseImport` (optional `note`, `role`, `publisher_name`; 409 `import_not_valid` unless valid) publishes **one version** (kind null: it covers every public kind) that replaces the public layers with the release's and **keeps the local layers**: the local populations and local results unchanged, and the studies and incidents sets rebuilt from the release's public records plus this instance's hospital records. A second import keeps them again (test). Tracked cards and defaults live in each browser's profile and are never touched. Serialized like a publish (409 `publish_in_progress`). A bundle whose rows the store's constraints refuse (only a hand-made one) answers 409 `invalid_bundle` and publishes nothing.

### 26.6 The version feed

`listDatasetVersions` (`GET /versions`, a read with `version`, ETag, and 304) serves `{dataset_version, versions}`: every published version up to the served one, newest first, with `version_id`, `published_at`, `kind`, `summary`, change `note`, and `publisher_role` (never the name or upload ids); `after=<n>` lists only newer versions, so an operational system can ask what changed since the version it last saw. The admin History (`listVersions`) stays.

Since v1.14 (§30) the optional `card=<model_version>|<use_case>` (URL-encoded) lists only the versions that changed that card, by exactly the rule of the catalogue's `last_updated` (§17: its metrics set, multimorbidity set, registry signature, safety incidents, or linked study records differ from the version before; the version that adds a card counts). The newest entry is the tile's `last_updated.version`; `after` combines with it. Each entry is the feed's own, unchanged. A card no version holds gives an empty list; a value without exactly one `|` between a model version and a use case is 422 `invalid_parameter`. A read without `card` is byte for byte what it was. The API keeps the per-card version lists with the history behind `last_updated`, so a filtered read reads only the versions published since the last one.

## 27. Intervention effects (v1.13)

Added 2026-10-20 (release 0.4; concept in `docs/intervention-effects.md`). An **effect record** states what using an AI system changed for patients or for care, against a comparator, as measured by one study that compared care with and without the system. Predictive performance (§4) and effects are different evidence: **effects never enter a grade, status, Overview mark, warning, safeguard, comparison flag, summary, catalogue tile, or `last_updated`; the grades cover predictive performance only.** All effects are synthetic demonstration data.

- **Data set.** Kind `effects`: one global content set keyed by `effect_id` (letters, digits, `.`, `_`, `-`; at most 64), like `safety` (§18) and `studies` (§22). Before the first effects publish the store has no effects set and no concept has effects. Replace and merge uploads (§11.2: an empty Action adds or replaces, `Remove` deletes; there is no older-study rule), the records upload (§11.4; the Data Library's one-effect form uses it), staged reads, history, and rollback work as for the other kinds. Stored in the table `effects` (migration `0009`); codes and their anchor conditions as JSON arrays.
- **Fields** (template columns in parentheses; readable labels and codes are both accepted):
  - `effect_id` (Effect ID); `study_id` (Study ID): a `study_id` of the live studies set; its `design` must be `randomized_trial`, `prospective`, or `real_world_deployment`.
  - `model_version` (Model version) and `use_case` (Function): the card, in the live registry or a staged registry upload (note `configuration_not_published`), as for incidents.
  - `codes` (ICD-11 codes): ICD-11 codes of level-2 concepts, each stored with its depth-1 anchor in `condition_ids`; or one whole chapter (`chapter 11`), stored as `chapter_id` with no codes (§18 rules).
  - `outcome` (at most 200), `outcome_type` (`benefit`, `harm`, `process`), `population` and `comparator` (free text, at most 280 each).
  - `effect_measure`: the ratios `risk_ratio`, `odds_ratio`, `hazard_ratio` (no effect = 1) and the differences `risk_difference`, `mean_difference`, `standardized_mean_difference` (no effect = 0); `estimate`, `ci_low`, `ci_high` (the 95% interval; all three required); `unit` (optional, at most 40, e.g. "minutes"; an addition to the D13 field list so a difference can be read); `direction` (`higher_is_better`, `lower_is_better`); `follow_up` (optional, at most 120).
  - `appraisal_tool` (`rob2`, `robins_i`) and `judgement` (`low`, `some_concerns`, `high`, `critical`, `unclear`); `notes` (optional, at most 500).
- **Validation** (blocking errors with a plain fix): `unknown_effect_study` (no such study: add and publish it under Studies first), `effect_study_design` (a vignette, simulation, benchmark, or retrospective study), `appraisal_tool_mismatch` (a randomized trial needs RoB 2, the other designs ROBINS-I), `judgement_not_in_tool` (Critical with RoB 2), `effect_ci_order` (`ci_low ≤ estimate ≤ ci_high` fails), `effect_ratio_not_positive` (a ratio value ≤ 0), `unknown_outcome_type`, `unknown_effect_measure`, `unknown_effect_direction`, `unknown_appraisal_tool`, `unknown_effect_judgement`, `unknown_configuration`, `unknown_icd_code`, `missing_value`, `invalid_value`, `not_a_number`, `duplicate_key`. Notes: `configuration_not_published`, `nothing_to_remove`, `formula_like_text`. The database checks the CI order, positive ratios, and Critical with ROBINS-I again. Staged effects uploads are checked again after a registry or studies publish or rollback.
- **Attachment.** A concept shows the effects of the card read that concern it: a depth-1 condition those naming it (or its chapter); a deeper category those of its anchor; a block or chapter those of any of its depth-1 conditions. Effects have no lens: the same effects show at every lens and population. In another ontology (§23) a concept shows the effects of the ICD-11 anchors it reaches (a `none` mapping shows none). A study removed or changed later leaves the stored effect as it is; reads then carry `study` null (the Data Library's check of a new upload refuses it).
- **Reads.** `getConceptMetrics` adds `effects` (a list of `Effect`, in stored order) after `incidents`, **only when the list is not empty**, so every read of a store, card, or concept without effects is byte for byte what it was. Each `Effect` carries the record and `study`, the `Study` record of the version (or null). `listEffects` (`GET /effects`, tag `studies`) serves `{dataset_version, effects}`: every effect of the version in stored order, optionally of one AI system (`model`) or one card (`model` and `use_case`); a filter that matches nothing gives an empty list. It takes `version` (live or staged), carries `X-Dataset-Version` and an ETag, and takes no `population` or `ontology`. `exportConcept`, the map, summary, catalogue, comparison, lookup, and dataset export carry no effects.
- **Change summary (§11).** Rows compare by effect id (added, changed, removed; a merge's `unchanged` counts the records it touched); samples name `<effect_id>: <outcome>` with the first condition or chapter and code. No status shifts. The version summary reads "Effects on outcomes: N effects added, …".
- **Static demo.** Recorded: `listEffects` whole, and the recorded condition cards carry their effects, so the static condition card shows the effects section.
- **Frontend.** The condition card shows **Effects on outcomes** after "Study quality", only when `effects` is present: per effect the outcome and type, one plain sentence against the comparator (better, worse, or no clear difference, by where the interval lies), a small effect plot (no effect in the middle; a log scale for ratios; the better side named; no status zones or colours), the design and judgement, and the study; at expert depth the measure with its interval and the study's details; and the fixed line "Not part of any grade. Grades on this card cover predictive performance only." The Summary panel says once that grades cover predictive performance only. The Data Library has the data set **Effects on outcomes** next to Studies.

## 28. Configurations and lineage (v1.14)

Added 2026-10-22 (release 0.5; criteria G1, G11, G13). A card is still one AI system with one function (`card_id` unchanged); these fields say how it is deployed, what its figures measure, which earlier version it supersedes, and what the developer declares about data protection. They are registry fields (§11.1), versioned with the registry, and **never change a grade, status, score, or comparison flag** in this phase. All data is synthetic demonstration data with fictional names.

### 28.1 Configuration record

- **Fields** (one value per model × use case; template columns in parentheses; all optional):
  - `configuration_id` (Configuration ID): a label of letters, digits, `.`, `_`, `-`, at most 64 characters (e.g. `cfg-2026-09`); `configuration_date` (Configuration date): an ISO date `YYYY-MM-DD` (XLSX date cells accepted).
  - `prompt_summary` (Prompt summary, ≤ 500 characters): a **summary** of the instructions the system is given, never the full prompt; `prompt_sha256` (Prompt SHA-256): the SHA-256 of the full prompt, 64 hex characters, stored and served in lower case (upper case is accepted).
  - `retrieval` (Retrieval, ≤ 280); `tools` (Tools): at most 10 names separated by `;` in files, each at most 60 characters, repeats dropped; a list in the API, empty when none.
  - `sampling_temperature` (Sampling temperature, 0–2), `sampling_top_p` (Sampling top-p, 0–1), `sampling_max_output_tokens` (Max output tokens, a whole number ≥ 1); `fine_tuning` (Fine-tuning, ≤ 280).
  - `performance_measure` (Performance measure, ≤ 200, e.g. "Top-3 diagnostic accuracy") and `reference_standard` (Reference standard, ≤ 200, e.g. "Final diagnosis at discharge"): what the card's Performance figures measure and against what. Comparison groundwork (F6): since phase Q4 the comparison's card facts carry them and the reasons `measure_differs` and `measure_unknown` read `performance_measure` (§25).
  - Data-protection declarations (F8): `declared_data_use` (Declared data use, ≤ 500), `declared_data_location` (≤ 200), `declared_retention` (≤ 200), `declared_privacy_contact` (≤ 200). The developer's statements, shown as "Declared by the developer" and never verified.
- **Validation** (blocking errors with a plain fix, on the cell): `invalid_configuration_id`, `invalid_date`, `invalid_sha256`, `too_many_tools`, `out_of_range` (sampling outside its range, max output tokens below 1), `not_a_number`, `not_a_whole_number` (max output tokens), `invalid_value` (too long, a line break, or a tool name over 60 characters), and `unknown_function_category` for a category outside the six. Readable labels and codes are both accepted for the category.
- **Reads.** `listModels` and the catalogue (each tile, §17) send, per card, `configuration`: an object with **every** field of the record (null where not given; `tools` an empty list) when at least one of them is given, and `performance_measure` and `reference_standard` each when given; `declarations` carries the four data-protection declarations, all four, when one of them is given (and is non-null then). Absent fields are left out, never sent as null, so **every read of a store, entry, or card without them is byte for byte what it was under v1.13** (test, digests recorded with the v1.13 code). Since phase Q4 the comparison's card facts (§25) carry `performance_measure`, `reference_standard`, and the configuration's id and date; the lookup (§19) and the exports do not carry them yet.
- **Storage.** Nullable columns on `use_case_variants` (`tools_json`, a JSON list; migration `0011_registry_fields.sql`); content sets stay immutable. A filled template carries every field, so uploading one unchanged gives no changes.
- **Freshness (§17).** The fields are part of the configuration's registry signature: a registry publish that changes any of them (a new `configuration_id`, for example) moves that card's `last_updated` and marks it `staged_change` in a staged read. The registry change summary counts the card as changed and names it in its samples.

### 28.2 Lineage

- **Field.** `replaces` (template column Replaces; an entry field, the same on every row of the entry, `inconsistent_value` otherwise): the model version this AI system supersedes, for example an earlier release of the same product.
- **Rules** (blocking errors with a plain fix, on the entry's first row): `replaces_self` (the entry names itself); `unknown_replaces` (it names no other entry of the same file; for a developer submission's registry part, a merge into the live registry (§26.3), no entry of the file or of the live registry); `replaces_cycle` (following `replaces` from an entry comes back to it, e.g. A replaces B and B replaces A; every entry of the loop in the file is named, with the loop written out). A chain (C replaces B, B replaces A) and several successors of one entry are allowed. A replace upload that leaves out an entry another one names fails `unknown_replaces` on the naming entry.
- **Reads.** `ModelEntry` (`listModels`) and `CatalogueTile.system` carry `replaces` when given and the derived `replaced_by`, the model versions of the registry whose `replaces` names this entry, in registry order, when not empty. `replaced_by` is derived, not a field of the entry: gaining a successor does not change an entry's registry signature.

### 28.3 Instance note

`InstanceProfile.data_protection_note` (§26.2): the hospital's (or public service's) own note on data protection, beside the developer's declarations. Optional, ≤ 500 characters, set on the Data Library's Instance page; sent in `/meta.instance` only when set. Not a dataset version.

### 28.4 Frontend

- **About this AI system** (the atlas's Summary) shows **Configuration**: at plain depth the configuration id and date and a one-line prompt summary; at expert depth every field (retrieval, tools, sampling, fine-tuning, the SHA-256), plus **What the figures measure** (performance measure, reference standard) when given. **Versions** shows "Replaces X" and "Replaced by Y", each a link to that AI system's card in the atlas, and **Compare with previous version** opens `compare.html` with this card and the previous version's card of the same function (else its first card). The data-protection declarations appear under "Declared by the developer", marked as declared, never verified.
- **Catalogue.** A tile of an AI system that replaces another says "Replaces X" in one quiet line. The filter **Newest versions only** (off by default; catalogue URL `newest=1`) hides the cards of AI systems that another entry replaces.
- **Model card** (DeveloperLabel, SVG and PDF): one line with the configuration id and date when given.
- **Data Library.** The registry templates carry the columns with readable labels and help; the Instance page edits the note.

### 28.5 Evidence age

Added 2026-10-22 (release 0.5). Which configuration and version a result was measured on, beside the card's current ones. **Information only:** it changes no grade, status, score, warning, mark, comparison flag, or `last_updated`.

- **State of one result.** A result rests on the study records its stored row links (§22): its own row (public or local), or for a lens fallback over several rows (§7) those of the rows it combined. Its configuration state, from each linked study's `configuration_id` against the card's `configuration.configuration_id` (§28.1):
  - `current`: every linked study evaluated the card's current configuration;
  - `earlier`: at least one evaluated another configuration (the registry records no order of configurations; one that is not the current one is read as earlier);
  - `not_stated`: otherwise, that is, a linked study states no configuration, or **the card states no configuration id**, so no study's configuration can be placed (a study that names one is still `not_stated` then).
- **Summary.** `getMetricSummary` adds `configuration_counts` `{current, earlier, not_stated}` (schema `ConfigurationCounts`) over the depth-1 conditions `appraisal_counts` counts as `linked`, on every view and in every ontology (another ontology's condition reads the studies of the ICD-11 conditions it serves). It is sent exactly when `appraisal_counts` is (§22), so every read without a linked graded condition is byte for byte what it was (`tests/test_evidence_age.py`).
- **Condition card (frontend).** For a stored row with a linked study, Study quality shows **Evaluated configuration**: "Current configuration (cfg-…)", "Earlier configuration (cfg-…; current cfg-…)", or "Not stated" (with the study's id when the card states none). When the study's `model_version` names another AI system than the card's, the card adds "Measured on <version>", or **Measured on an earlier version** (<version>) when that system is in the card's `replaces` chain (§28.2). No warning, mark, or status follows from either line.
- **Summary (frontend).** The Evidence view's Summary adds one card, "Evaluated configuration", with the three counts across the card's conditions at the lens.

## 29. Care settings (v1.14)

Added 2026-10-22 (release 0.5). The **care setting** is a lens axis beside age, sex, and ethnicity: the Context axis of the seed (`metric_axes.context`), which held one value, `Clinical`. All data is synthetic demonstration data.

- **Values.** `/meta.axes.context` lists `Clinical` first, shown as **Any setting**, then the specific settings in this order: `Emergency department`, `Intensive care`, `Inpatient ward`, `Outpatient clinic`, `Primary care`. They are the first five study setting categories (§22, `emergency_department` … `primary_care`; the sixth, `mixed`, has no lens value); the codes name a setting in the atlas URL (`setting=<code>`, `frontend/src/app/startupParams.js`) and in the lookup (`context.setting`, §19). `backend/app/schema/contract.py` (`CARE_SETTINGS`) holds the one mapping.
- **Storage.** The values are stored, not constants: the store's `axis_values` and `lens_combos` gain the five settings and their 450 lens combinations (`combo_idx = setting_idx × 90 + age_idx × 18 + sex_idx × 6 + eth_idx`, so every Any-setting combination keeps its index 0–89, §4.1). Migration `0013_care_settings.sql` adds them to a store imported before; the seed import adds the same after the seed's own axes (`tests/test_care_settings.py` checks that both agree). They are needed because every stored row (`metric_rows`, `set_combos`, row sources, study links, local results) refers to a lens combination by its index and foreign key, so rows at a setting need their combinations in the store. The seed is unchanged and holds Any-setting rows only.
- **Reads.** Every read that takes a lens takes `context` (§3): `getMetricMap`, `getMetricSummary`, `getConceptMetrics`, `getConceptSubgroups` (groups at the setting, compared with the setting's all-patients result), `getSubgroupSummary` (over the setting), `getComparison` (every column), `getMultimorbidityCandidates`, `getMultimorbidityCombination`, `exportConcept`, and the lookup's `context.setting`. `getCatalogue`, `getAtlasOverview`, `getChapter`, and `searchConcepts` take none: they describe the version and the prevalence, not a lens. Responses name the setting in `filters.context` (and each `MetricRow.context`). ETags and every server cache (response cache, per-card row caches) are keyed by the setting.
- **Semantics.** A specific setting reads **only the rows stored for it**. Where a card stores no row for the condition at the setting, or no row at that setting at all, the result is **No data** (`no_data`), never the Any-setting row. Within a setting everything works exactly as for Any setting: deeper categories through their anchor (§5), rollups over the conditions with a row at the setting (§6; a block or chapter without any is a rollup without children, presented as No data), the demographic fallback over narrower groups stored at the same setting (§7), the grade, score, status, warnings, and safeguards of each row (§4; no formula changes), study adjustments (§22), local results for a population (§26.1), and prevalence (§5, §21). Multimorbidity at a specific setting serves only combinations stored for that setting (§8; the demo stores none). Safety incidents have no setting: they mark a card at every setting (§18). Effects (§27) are not lens-bound and are listed at every setting.
- **Unchanged answers.** Without the parameter, or with `context=Clinical`, every read is byte for byte what it was before the axis was selectable, also for a card that stores rows at a specific setting (Any-setting combinations, counts, and facts leave the other settings out). Only `/meta.axes.context` lists the new values, and `listModels` and the comparison's card facts carry the additive `settings` of a card that stores a specific setting. The dataset export (§14) of such a card adds its setting rows under their own keys.
- **Facts.** `listModels` adds `settings` to a function's entry, and `getComparison` to a card's `lenses`: the settings the card's rows are stored for (its public metrics; in the comparison also its local results for the chosen population), `Clinical` first, **only when one is specific**. A card without `settings` stores Any setting only.
- **Comparison.** `population_differs` (§25) also covers a card that stores no rows at the requested specific setting while another card does. No separate reason: the facts' `settings` tell the reader which case it is. Q4's `setting_differs` compares the linked studies' setting categories (§22), not the lens.
- **Uploads.** Metrics and local results take the optional Setting column (§11): `unknown_setting` for other values, common lens coverage over Any-setting rows only, the change summary's `rows.settings` and samples' `setting`. Rows at a setting go through the normal upload → check → publish path (merge uploads with Source, Study, Source date; performance needs evidence as everywhere).
- **Budgets.** Unchanged (§10): no response over 2 MB; a setting switch reads one map and one summary.
- **Static demo** (release 0.5; §26.7). Each specific setting a card stores (`listModels` `settings`) is recorded **at all patients in ICD-11**: the atlas and chapter maps, the Summary of every view with the weighted shares, every condition card (per chapter), Across groups, and the group summary. The atlas's Setting choice lists every setting but offers only those the card on screen stores ("not in the static demo" beside the others); a `setting` URL parameter applies when the card stores that setting, else the atlas shows Any setting (and a plain-language setting chip says so in a notice). At a setting the population choice is fixed to all patients, and in another classification no setting can be chosen; both come back with Any setting and ICD-11, as the chosen group does. The adapter rejects every other combination with `static_unavailable` in words: a setting the card does not store, a setting with a group or in another classification, multimorbidity at a setting, and the comparison at a setting (the comparison page offers Any setting only).
- **Frontend.** The atlas toolbar's Population popover has a **Setting** choice (Any setting and the five; a setting the card stores nothing for stays choosable, marked "No data stored"), kept in the URL as `setting=<code>` by the atlas and the comparison and in links between them. The population line beside every result names a specific setting after the group ("All patients, Emergency department, default prevalence"; Any setting is not named), and the ring pane shows it as a chip and in the legend. When a specific setting has no result for the chosen concept, the condition card says **No data for this setting** and offers "Show the Any-setting result", read on demand through the data client and labelled "Any setting, not specific to <setting>"; it never takes the setting's place. The comparison page offers the same choice, and the live panel takes a `setting` attribute.

## 30. Audience reads (v1.14)

Added 2026-10-22 (release 0.5; criteria G7, G12, G13). Five audience presets (Clinician, Patient, Procurement and governance, Regulator, Payer) change where a card starts and which summary heads the atlas Summary, **never a figure**. Each audience summary is built only from figures other reads already serve; three additive reads supply what was missing. Nothing here is a grade, a ranking against other cards, or a statement that a system is safe or approved. All data is synthetic demonstration data.

### 30.1 Reads

- **Weighted distribution.** `getMetricSummary` with `weights=prevalence` adds `weighted_distribution`: for the depth-1 conditions (§5) at the requested lens, setting (§29), population (§21), and ontology (§23), each status's share of their total prevalence weight. A condition's weight is §6's rollup weight: its prevalence score (the local population's tier score for a population read), or 1 when the score is missing, not finite, or not positive. Keys follow the view's own counts: the five statuses of `counts` for `overall`, `performance`, and `evidence` (a condition counts under the status `counts` gives it); `in_scope`, `partially_in_scope`, `out_of_scope`, and `no_data` for `intended_use` (no row or no intended-use value is `no_data`); `serious`, `caution`, and `none` for `safety` (the marks of `safety_counts`). Shares are rounded to 4 decimals, half up, and sum to 1 up to that rounding. Example (the tiny test store): a common condition (score 0.45) that is Strong and a rare one (0.12) that is Weak give `strong` 0.7895 and `weak` 0.2105. The response is cached under its own key; without the parameter the summary, its ETag, and its cache entry are exactly what they were.
- **A card's versions.** `listDatasetVersions` with `card` (§26.6).
- **A card's incidents.** `listSafetyIncidents` (§18).

The block follows the lens, setting, population, and classification on screen, and every block ends with the synthetic-data notice. A part whose read the static demo does not record says so in words instead of a figure.

## 31. Plain-language search and synonyms (v1.14)

Added 2026-10-22 (release 0.5). A reader can type what they want to see ("heart failure in older women in the emergency department") and the atlas shows it as **chips** they can remove before anything is applied. Classification: ICD-11 only (the interpreter's conditions are ICD-11 concepts; other classifications search as §9 says). All data is synthetic demonstration data.

### 31.1 Synonyms

- **Sources** (`app/ontologies/synonyms.py`, run by the ontology import, §23): `mondo`, the label and EXACT synonyms of every MONDO condition whose own crosswalk (§23.2) reaches an ICD-11 concept directly (kind `exact` or `stem`; mappings inherited from a parent and mappings to a whole block give none); `icd10cm_index`, the main terms with a code of the ICD-10-CM index to diseases and injuries whose code reaches an ICD-11 concept by the ICD-10 rule (`exact` or `stem`). Index titles lose their nonessential modifiers (the words in parentheses); a title of inflected forms gives each form ("Infarct, infarction"), any other title stays whole ("Pharyngotracheitis, chronic"); subterms are left out (they qualify a main term and read poorly alone).
- **Each synonym** belongs to the level-2 ICD-11 concept the mapping names and keeps its source and the code it was read under (the MONDO id or the ICD-10-CM code). Dropped: one equal to the concept's preferred term, one shorter than three characters or longer than 200, one without a letter, and a repeat of another synonym of the same concept, compared case-insensitively with spacing collapsed (the first in import order wins; the search reads MONDO's first).
- **Reference data:** no publish, rollback, or upload touches them; a backend reads them once, with the ontologies (restart it after an import). A store without an import has none.

### 31.2 The interpreter (`interpretQuery`)

Deterministic: the same query, registry, axes, and synonyms give the same answer (`app/services/interpret.py`). The query is trimmed, its spacing collapsed, and cut at 200 characters; words are runs of letters and digits, compared in lower case. Each step reads only the words no earlier step took:

1. **Numbers and symbols** in the text: an ICD-11 code the atlas has (four characters with a digit third, optionally `.` and up to four more: "5A11", "BA00.0") is a condition (`match: "code"`). Ages give the age group whose range holds them: "70-year-old", "70 years old", "70 years of age", "70 yo" (that age); "aged 18 to 39", "ages 40-64" (the range); "65+", "aged 65+", "at least 65" (that age and older); "over 64", "older than 64", "above 64" (older than it); "under 18", "younger than 18", "below 18" (younger than it); "aged 30" (that age). An age range that spans two groups ("over 40") gives no chip and is listed as unrecognized. "A&E" is the emergency department.
2. **AI systems:** a run of up to six words whose letters and digits, without spaces, hyphens, underscores, or dots, spell a model version or display name ("syngpt 2.0", "SynGPT-2.0", "Vantrel Triage 2.1", "ICU_GPT-1.0"); or a family name, the name without its version ("SynGPT", "Vantrel Triage", "ICU_GPT") or its first word of four letters or more ("Vantrel"), which means the family's newest system (one no system of the registry replaces, §28.2; else the last in registry order). A name two systems share names none.
3. **Condition names that hold a vocabulary word:** two or more words, one of them a word of step 4's vocabularies, that are exactly a preferred term or a synonym ("male infertility", "skin cancer"), so that word is not read as a lens or function there.
4. **Vocabularies,** longest phrase first, then left to right (on a tie: function, setting, age, sex, ethnicity):
   - *Functions:* a function's own name ("Discharge letter generation"), or simple words: triage; discharge, discharge letter(s), discharge summary; documentation, scribe, clinical notes; radiology, imaging, x-ray, radiograph; image analysis; skin, skin lesion(s), dermatology, moles; decision support, clinical decision support, CDSS, diagnosis support; patient communication; administrative. A word names the functions whose name holds it (triage, discharge, radiolog, skin) or whose function category matches (§11.1). With one system named, the function is one of that system's (none: the words are unrecognized); otherwise the default system's, else the first in registry order.
   - *Care settings* (values of the Context axis after Any setting, §29; a store whose axis lists none gives no setting chip): emergency, emergency department, emergency room, ED, accident and emergency, casualty → Emergency department; ICU, ITU, intensive care (unit), critical care → Intensive care; ward(s), inpatient(s), hospital ward, hospitalised → Inpatient ward; outpatient(s), clinic(s), outpatient clinic, ambulatory → Outpatient clinic; primary care, GP(s), general practice, general practitioner, family practice, family doctor, family medicine → Primary care.
   - *Age:* children, child, paediatric/pediatric, kids, teenager(s), teens, adolescent(s), infant(s), baby/babies, newborn(s), toddler(s), minors → Age 0-17; young adult(s) → Age 18-39; middle-aged, middle age, midlife → Age 40-64; older, elderly, the elderly, senior(s), older adults/people/patients, geriatric, pensioners, retirees → Age 65+.
   - *Sex:* women, woman, female(s), girl(s), ladies → Sex Female; men, man, male(s), boy(s), gentlemen → Sex Male.
   - *Ethnicity:* white, caucasian(s) → White; black, African American(s) → Black; hispanic(s), latino/latina/latinx → Hispanic; asian(s), south asian, east asian → Asian; other ethnicity, mixed ethnicity → Other. Only values on the axes count.
5. **Conditions** in what is left: the words are split at "and", "with", "or", "plus", "vs", commas, semicolons, slashes, and at every word an earlier step took. In each part, the longest run of words (at most six; not starting or ending with a stopword) that names a concept becomes a condition, and the rest of the part is read again. A run names the concept whose code it is; else the concepts whose preferred term is the run; else those with a synonym that is the run (shorter synonym, lower level, preferred term); else those whose preferred term holds the run as whole words (in search order, §9). A run inside a longer synonym does not count. A **single word** must have three letters, not be a generic word (disease, disorder, syndrome, condition, problem, illness, other, specified, unspecified, chronic, acute), and be a code, a whole preferred term or synonym, or the first word of a chapter or block named "<word> or …" ("epilepsy" is "Epilepsy or seizures"; "pain" or "chest" alone is no condition). A condition found by a synonym opens as its depth-1 condition when the synonym names a subcategory ("heart attack" → BA41.Z → **BA41 Acute myocardial infarction**), since a subcategory shares its condition's result (§5). At most **three** conditions; further ones are unrecognized.
6. Words no step took and that are not stopwords (articles, prepositions, and words such as patients, people, results, performance, model, system, care, age, years) or splitters are **unrecognized**, as runs of adjacent words in query order.

**Cancelling.** Two different values for one kind (two systems, two sexes as in "men and women", two age groups) give no chip for that kind, and their words are listed as unrecognized. The same value twice gives one chip.

**Answer** (`Interpretation`): `query` (the tidied query), `chips` ordered by kind (system, function, condition, sex, age, ethnicity, setting), then position, and `unrecognized`. A chip has `kind`, `value` (a `model_version`, a `use_case`, a `concept_id`, a lens value, or a Context axis value), `label` (plain words: the display name, the function, the preferred term without a leading "- ", Women or Men, the group without "Ethnicity "), and `matched_text` (the words of the query it was read from). A condition adds `code`, `pt`, `match` (`term`, `synonym`, `code`), `matched_term` (synonym matches), and `concept` (the ICD-11 concept record). Nothing is applied: the reader sees the chips and applies them.

**Reads:** `version` (§2) as everywhere; the answer depends on the version's registry and axes, so its ETag and response cache are keyed by them. 422 `invalid_query` for a query that is empty after trimming or longer than 200 characters.

### 31.3 The helper rewrite (`interpretQueryWithHelper`)

Optional, off by default (§20). The provider answers with chips of the same kinds and the words it could not place; the backend keeps a chip only when its value is in the vocabularies (a system by model version or display name; a function, with one system named, one of that system's; lens and setting values of the axes) or, for a condition, when the value names a concept by step 5's rules (a code, a name, a synonym; the provider never adds a concept the atlas lacks). Others are listed in `dropped` with the reason `unknown_kind`, `unknown_value`, `not_found`, `conflict` (two values for one kind), or `limit` (a fourth condition). A chip's `matched_text` is kept only when those words are in the query. The answer is not cached and never contains the key.

### 31.4 Frontend

- **Atlas search palette** (ICD-11 only): a query of three or more words, or one with a recognized system, function, age, sex, ethnicity, or setting chip, shows an **interpretation row** above the results: the chips, each removable, and **Apply**. Apply sets the card (a system or function chip; a function alone keeps the system on screen when it has that function, else the first system that does), the lens, and the setting, and opens the first condition; with two or three conditions on a card with stored combinations it offers **Open as a combination** (Multimorbidity mode). Removing a chip applies the rest. Synonym matches in the result list say "also known as <matched term>".
- **Catalogue:** an **Ask** field reads the same query; Apply opens the atlas with the chips' state in the URL (`model`, `use_case`, the lens, `setting=<code>`, `concept`, or `mode=multimorbidity` with `selected`).
- **Ask with the helper** appears in the palette only while the helper is on (§20); its chips replace the rule-based ones until the query changes, marked as the helper's.
- **Static demo** (§26.7): since release 0.5 the static build records the ICD-11 synonyms (`synonyms.json`: each concept's synonyms in `load_synonyms` order, 14,162 on the demo store, 0.44 MB, 0.1 MB gzipped), so its search matches them ("also known as") exactly as the API does, and `interpretQuery` runs a port of these rules (`frontend/src/api/staticInterpret.js`) over the recorded registry, axes (setting chips included), and that search. The recorder compares the static search (synonym matches included) and the static interpreter with the API at every recording, the 30 queries of §31.5 among them. `interpretQueryWithHelper` is `static_unavailable`. Shared cases (`backend/tests/fixtures/interpret_rule_cases.json`) run through both.

### 31.5 Quality

A fixed set of 30 synthetic queries (`backend/tests/fixtures/interpret_queries.json`) is read on the demo store with the pinned ontology files imported: at least 27 must give exactly the expected chips and unrecognized words (measured: 30 of 30). The static port reads the 18 that need no synonym the same way without synonyms (measured: 18 of 18), and all 30 exactly as the API with the synonyms the static demo records (checked at every recording, §31.4).

## 32. Card record and evaluation import (v1.14)

Added 2026-10-22 (release 0.5; criteria G9, G13). A compact record of one card for operational systems, the same record as JSON-LD, and a way in for results of benchmarks and evaluation harnesses run outside the product. **No grade changes:** the record serves what the other reads serve, and imported results reach the store only as ordinary records, staged, checked, reviewed, and published. All data is synthetic demonstration data with fictional names.

### 32.1 Card record (`getCardRecord`)

- **Read.** `GET /cards/record?model=&use_case=` (tag `cards`), with `version` (live or staged, §2), a strong `ETag`, `X-Dataset-Version`, and 304 like every read. It takes no `population`, `context`, lens, or `ontology`: the record is the **public ICD-11 card at all patients, Any setting, and the default prevalence**, so every operational system reads the same record for a version. An unknown card is 404 `unknown_model` / `unknown_use_case`; a missing `model` or `use_case`, or a `format` other than `json` or `jsonld`, is 422.
- **Body** (`CardRecord`, `format: "bmc-card-record/1"`):
  - `dataset_version`, and `generated`: the notice "Synthetic demonstration data. Not a certification, an approval, or evidence about any real AI system. Not for clinical use.", `/meta`'s `synthetic_data_notice`, the classification (`ICD-11 MMS`), the lens (as the catalogue states it), and the prevalence (`default`).
  - `card_id`, `model_version`, `use_case`, and `system`: the AI system as the catalogue tile serves it (kind, AI type, developer, release, description, `built_on`, and `replaces` / `replaced_by` when given, §28.2).
  - `card`: function category, whether it is the system's default function, `intended_use_defined`, `declarations` (data protection included, §28.1), `has_multimorbidity`, `last_updated` (§17), and `configuration`, `performance_measure`, `reference_standard` when given.
  - `summary`: the Overview counts over the depth-1 conditions, `overall`, `performance`, `evidence`, and `intended_use` exactly as the catalogue tile's distributions (so `overall` equals `/metrics/summary`'s `counts`), `condition_count`, and `safety`: the conditions by safety mark (`serious`, `caution`, `none`).
  - `chapters`: every chapter in atlas order with its id, number, name, `condition_count`, the status of each view from the chapter's rollup row (`overall`, `performance`, `evidence`; `intended_use` its level or `no_data`, null for a card without an intended-use statement), the rollup's `perf` with `ci_low` and `ci_high`, its `safety` mark, and `overall_counts` (its conditions by Overview status, the tile's chapter counts). A rollup without children reads `no_data` with null values (§6, V1), as clients present it.
  - `studies`: the **public** study records the card's stored rows name (§22's link), in stored order; `effects`: the card's effects on outcomes (§27, as `listEffects` serves them); `incidents`: the card's **public** safety incidents, newest first (§18). A hospital's own studies and incidents are a local layer (§26.1) and are left out, as a public release bundle leaves them out (§26.5); the `safety` marks above follow the listed incidents only.
  - `links`: `atlas` (the card on the atlas at `view=overall`, relative to the frontend root, §19's link form), `record` and `record_jsonld` (API paths), and `narrow_model_card` (the API path of the developer's narrow model card, §26.4, or null when none is published).
- **Budget** (§10): under 300 KB, as JSON and as JSON-LD (test over every demo card; about 10–20 KB).
- **Frontend.** The Summary's footer offers **Card record (JSON)** beside the dataset export; it downloads the record of the card on screen (`getCardRecord` through the data client). The static build records both forms per card (release 0.5; §26.7) and offers the download, without the dataset export.

### 32.2 Evaluation results import (`createEvaluationUpload`, `getEvaluationProposals`)

- **Format** (`bmc-evaluation-results/1`; `docs/evaluation-results.md`, example `docs/evaluation-results-example.json`): one JSON object for one card: `format`, `model_version`, `use_case`, `configuration_id` (the configuration the run evaluated; letters, digits, `.`, `_`, `-`, at most 64), `benchmark` `{name (≤ 120), version? (≤ 40), description? (≤ 280), url? (http or https)}`, `run_date` (YYYY-MM-DD), `conducted_by` (`developer`, `independent`, `hospital`), optional `setting` (a study setting category, §22: the five care-setting codes or labels, or `mixed`), and `results`: 1 to 5,000 objects `{icd11_code, measure (≤ 200), value (0–1), ci_low?, ci_high? (0–1), cases (whole number ≥ 1), sites? (whole number ≥ 1), age?, sex?, ethnicity?}`; lens values are the atlas's axis values and default to All. Unknown keys are refused, at the top level, in `benchmark`, and in a result, so nothing a harness writes is silently dropped (and no identifier rides along).
- **Upload.** `createEvaluationUpload` takes `{content, filename?, submission_id?, replace_staged?}` (at most 1 MB, else 413 `upload_too_large`), stages an Upload of kind `evaluation_results` whose target is the card the file names (null when it names none), and checks it in the background like a narrow model card (§26.4). The upload is never a data set (§11). Like a narrow model card's, it has no checked copy: `downloadAnnotatedUpload` answers 409 `upload_not_valid`, and its problems are in its report.
- **Check** (blocking errors, each with a plain fix): `invalid_evaluation_file` (not UTF-8, not JSON, not one object, nested too deeply, larger than 1 MB, or another `format`); `evaluation_field` (a missing, malformed, unknown, or too long field; who conducted the run; the setting; an empty `results`); `unknown_target` (a card in neither the live registry nor a staged registry upload; the note `target_not_published` when only staged); `unknown_icd_code` (a code that is no ICD-11 condition or subcategory of the atlas: chapters, blocks, and codes of other classifications are refused); `out_of_range` (a value, bound, or count outside its range), `not_a_number`, `not_a_whole_number`; `ci_low_above_ci_high`, `perf_outside_ci` (the CI order); `unknown_lens_value`; `duplicate_key` (two results for the same condition, its subcategories included, and group). Examples give `row` 0 for the file and the result's position + 1 for a result, and the field in `column`.
- **Notes** (never blocking): `measure_differs_from_card` when a result's `measure` differs from the card's `performance_measure` (§28.1), ignoring case and spacing (as the comparison's `measure_differs`, §25); none when the card states no measure. `configuration_not_current` when `configuration_id` is not the card's current `configuration.configuration_id` (or the card states none). Both say what the reader of the card will see; neither changes a grade.
- **Proposed records** (`getEvaluationProposals`, `GET /admin/uploads/{upload_id}/evaluation-proposals`; valid evaluation results only, 409 `upload_not_valid` otherwise, 409 `upload_outdated` when the live data no longer fits the file). Nothing is staged:
  - `study`: one record in the studies template's keys (§22): `study_id` `EVAL-<benchmark and version, words in parentheses left out>-<run date>` (upper case, at most 64; the same run proposes the same id, so importing it again replaces that record), title from the benchmark and the AI system, design `benchmark`, `conducted_by` from the file, the free-text setting and `setting_category` from `setting`, `sites` the most sites any result names (else 1), `patients` the sum of the results' cases, peer reviewed No, reporting guideline None, risk of bias `unclear` (with the note that a reviewer should judge it), population from the benchmark's description, evaluation conditions naming the run date, measures, result count, and configuration, `model_version`, `publication_date` the run date, `source_url` the benchmark's URL, and `configuration_id`.
  - `metrics`: one merge record per result for the card (`model_version`, `use_case`, `records`): the result's condition (a subcategory as its depth-1 anchor, §5) at its lens and Any setting, Performance the value, CI the bounds, Samples the cases, Sites, Studies 1, Peer-reviewed studies 0, Validation type Benchmark, Source "Evaluation run: <benchmark> <version>", Study the study id, Source date the run date; the stored row's intended-use fields and warnings are kept (a merge row replaces the whole row, §11.2, as for narrow model cards, §26.4), except the warnings that said the stored row had no data (`no_performance_data`, `no_validation_data`).
  - `results` (each result's position, code as written, condition, and measure) and `notes` (the check's notes).
- **Staging.** The maintainer (Performance metrics page, **Import evaluation results**) or the custodian (a submission's part, §26.3) ticks what to stage. The study is staged and published first, through the studies records upload; then the metrics merge that names it, through the metrics records upload (§11.4). Each is checked, reviewed, and published like every upload (the newest-study rule of §11.2 applies). **Nothing publishes on its own.** Once published, the rows link the benchmark study (§22): its risk of bias `unclear` lowers their evidence signal by the approved −0.04, and the condition card's Study quality and Evaluated configuration (§28.5) name it.

## 33. CDS Hooks service (v1.14)

Added 2026-10-22 (release 0.5; criteria G10, G13). A local service shaped like CDS Hooks 2.0, so a host application on this machine can ask where a synthetic patient's conditions sit on one card. **Demonstration on synthetic data, not for clinical use:** every card says so, and the service is behind the local-only guard (§16) with no CORS. It reuses the lookup (§19) and the ICD-10-CM crosswalk (§23); no FHIR library, no outbound request.

- **Discovery** (`getCdsServices`, `GET /cds-services`, tag `cds-hooks`; a read with `version`, ETag, `X-Dataset-Version`): `{services: [{id: "bmc-condition-status", hook: "patient-view", title, description, prefetch: {patient: "Patient/{{context.patientId}}", conditions: "Condition?patient={{context.patientId}}"}, usageRequirements, extension: {"broad-modelcard": {dataset_version, default_card: {model_version, use_case}, notice}}}]}`. The service fetches nothing itself: a request must carry both prefetch entries.
- **Request** (`callCdsService`, `POST /cds-services/bmc-condition-status`, `version` as a query parameter; at most 64 KB, else 413 `upload_too_large`). The JSON is parsed by hand and only these fields are read; every other field of the request and of the FHIR resources is ignored and never echoed:
  - `hook` `patient-view`; `hookInstance` (1–128 characters); `context.patientId` (a string; not used beyond the check);
  - `prefetch.patient`: a FHIR `Patient` or absent; `birthDate` (`YYYY`, `YYYY-MM`, or `YYYY-MM-DD`, not in the future) gives the coarse age group of §19 (0-17, 18-39, 40-64, 65+, by the age today); `gender` `female` or `male` gives the sex group, `other` and `unknown` (or none) all sexes. Ethnicity is not read (all ethnicities).
  - `prefetch.conditions`: a FHIR `Bundle` with 1 to 12 `entry[].resource` of type `Condition`; each condition's first `code.coding` whose `system` is ICD-11 MMS (`http://id.who.int/icd/release/11/mms`) or ICD-10-CM (`http://hl7.org/fhir/sid/icd-10-cm`) is read (`code` letters, digits, and dots; `display` optional).
  - `extension["broad-modelcard"]` (optional): `card_id` (`<model_version>|<function>`; absent: the registry's default AI system and its default function, as discovery names them), `setting` (a care setting's code, §29), and `population` (a local population id, §21; the response then carries `X-Population`).
  - A malformed request is **400** `invalid_cds_request` with a plain message that names the field and never the value sent; an unknown card 404 `unknown_model` / `unknown_use_case` ("Unknown card."); an unknown population 404 `unknown_population`.
- **Mapping.** An ICD-11 code is the atlas concept with that code, else its stem (the last character after the dot dropped, repeatedly, §23.2). An ICD-10-CM code reads under its own ICD-10-CM concept, else its four-character, else its three-character category (codes of five or more characters are not in the classification, §23.1), and takes that concept's crosswalk mapping (§23.2): `exact` and `stem` reach an ICD-11 condition, `block` an ICD-11 subchapter (its rollup is reported), `none` nothing. The store must have imported ICD-10-CM; otherwise ICD-10-CM codes are unmapped.
- **Response** (`CdsResponse`): `{cards: [...]}`, **one card per condition, in request order**, `Cache-Control: no-store`, `X-Dataset-Version`. A mapped condition's card reads what `lookup` serves for it at the lens and setting:
  - `uuid` (random), `summary` (at most 140 characters: the condition's display name (from the coding, else the classification's name), its Overview status in words "on this card", and "serious safety incident open" or "safety incident open" when one applies), `indicator` (`critical` for a Serious mark; `warning` for a Caution mark or an Overview status of Weak, No data, or Out of scope; else `info`);
  - `detail`: short markdown: the status of each view (Overall, Performance, Evidence, and Intended use when the card states one), the lens in words, the mapping when an ICD-10-CM code was mapped, the top three warnings and two safeguards (their short titles), the open incidents (up to two, Serious or Caution with their synthetic summary, and how many more), and the line "*Demonstration on synthetic data, not for clinical use.*";
  - `source.label` "Broad Modelcard (synthetic demonstration)"; `links`: one `absolute` link to the condition on the atlas, built from the request's own origin (`Origin` when the browser sent one, which the guard requires to be the request's own, else `scheme://Host`), so a request through the app's server opens its atlas;
  - `extension["broad-modelcard"]`: the coding's system and code, `matched`, the ICD-11 `concept_id`, the `statuses`, the `safety` mark, the `dataset_version`, and for ICD-10-CM the `mapping` (`kind`, `icd10cm`, `icd11_concept_id`).
  - A condition without an ICD-11 or ICD-10-CM coding, with a code the atlas lacks, or with a mapping `none` gives one `info` card ("<code> (ICD-10-CM): no mapping to the atlas") that says why, links to the card, and carries the synthetic-data line. A rollup without children reads No data (V1).
- **Privacy.** As for `lookup` (§19): the case travels in the POST body; nothing of the request is stored, cached, or logged (an unexpected error is logged by its type only), and problems name fields, never values. The request should carry synthetic patients only; it is never sent anywhere.
- **Frontend.** The Live interaction page (`plugin.html`) has a **CDS Hooks request** mode: it builds the request from the synthetic case form (a synthetic birth date from the age group, the sex as gender, the codes as ICD-11 or ICD-10-CM codings, the card and setting in the extension), shows it, sends it on request through the data client, and shows the returned cards (indicator, summary, detail, link) and the response. Not in the static build.
